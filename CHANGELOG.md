# Changelog

## 0.29.0 — 2026-11-12

**Сервер теперь живёт в самом приложении (вариант A) — вместе с общей библиотекой
(вариант D).** Приложение поднимает Node-рантайм и HTTP-сервер у себя на телефоне:
полный доступ к `/api/health`, файлам и перемотке без внешнего сервера. Общая
библиотека при этом не выключается — треки других устройств по-прежнему приходят
через реестр в любой сети. Подробности: `docs/EMBEDDED.md`.

### Почему Node 24, а не npm-пакет

`nodejs-mobile-react-native` в npm — Node 18, а серверу нужен `node:sqlite`
(Node 22.5+, в 24 — release candidate). Поэтому берём сборку
`RockinChaos/nodejs-mobile` v24.22.3 (16 КБ страницы памяти, требование Android 15+),
а мост пишем сами: нужен только `node::Start` в потоке, без протокола сообщений.

### Что появилось

- `apps/mobile/nodejs/embedded/bootstrap.mjs` — точка входа в Node: HTTP-сервер
  (`/api/health`, `/api/files`, `PUT/DELETE /api/files/library/*`, `/files/*` с
  `Range`, `POST /api/shutdown`), запись `state.json`, обработка падений;
- `apps/mobile/nodejs/android/vision-node-jni.cpp` — JNI-мост, stdout/stderr в logcat;
- Kotlin: `VisionNodeModule` (`NativeModules.VisionNode`), `VisionNodeService`
  (foreground-сервис), распаковка `bootstrap.mjs` из assets;
- `apps/mobile/src/runtime.ts` — запуск/остановка/чтение состояния; сервер стартует
  сам при запуске приложения и никогда не роняет экран, если рантайма нет;
- `src/lib/embedded-server.ts` — порты (4000…4010), `EADDRINUSE` → соседний порт,
  состояния и тексты (11 тестов);
- экран **«Сервер на телефоне»**: состояние, адрес, версия Node, причина отказа,
  запуск и остановка (состояние читается из `state.json`, а не из факта вызова JNI);
- **встроенный тестер API**: шесть проверок (health, список, загрузка, скачивание,
  `Range`, удаление), отчёт с копированием/шерингом (8 тестов);
- **тестовый APK `VisionTester`**: свой `applicationId`
  `app.vision.audio.tester`, ставится рядом с обычным приложением, содержит Node и
  тестер (`scripts/android-tester-app.mjs`, job `tester` в CI);
- скрипты сборки: `scripts/fetch-nodejs-mobile.mjs` (кэш в CI по версии),
  `scripts/android-embed-node.mjs` (идемпотентное вживление, `--check` для CI);
- проверка APK в CI: наличие `lib/arm64-v8a/libvisionnode.so`, `libnode.so` под три
  ABI и `assets/nodejs-project/bootstrap.mjs` — иначе сборка без Node помечается
  предупреждением, а не выдаётся за рабочую.

### Стабилизация первых APK

- Node теперь запускается только в отдельном Android-процессе `:vision_node`; JNI и
  `libnode.so` не загружаются в процесс React Native. Падение V8/Node не должно
  закрывать приложение и плеер.
- Имя сервиса в манифесте стало полным (`app.vision.audio.node.VisionNodeService`):
  относительный `.node.*` ломал тестовую сборку с `applicationId app.vision.audio.tester`.
- Запуск считается успешным только после реального `/api/health`; зависший `starting`
  и старый `running` диагностируются по таймауту/health-check.
- Возвращена production-конфигурация `app.json` (`app.vision.audio`, `visionaudio`);
  `VisionTester` получает отдельный id и схему только через сборочный скрипт.
- Убрана module-level зависимость тестера от `TextEncoder`: экран тестера импортируется
  при запуске плеера, поэтому отсутствие API Hermes могло закрыть оба APK до первого
  кадра. Тело тестового upload отправляется как `ArrayBuffer`.

### Ограничения

Сервер собран вокруг диагностического режима: полный `services/api` в APK пока не
упакован (`mode: "diagnostic"`, не сделано L2). iOS — как раньше: локальный плеер и
реестр. `ffmpeg` в APK нет.

## 0.28.0 — 2026-11-12

**Одна библиотека на всех устройствах — в любой сети.** Загрузили пять песен на
телефоне — второе устройство с приложением сразу видит их в ленте. Не только по
домашнему Wi-Fi: в мобильном интернете, в гостях, где угодно.

### Почему не «сервер на каждом телефоне»

Владелец просил, чтобы каждое устройство выступало сервером. Буквально это не
работает: за NAT оператора до телефона нельзя достучаться, адрес меняется при
каждом переподключении, а ОС усыпляет приложение и закрывает входящие сокеты. В
разных сетях два телефона не видят друг друга вообще. Поэтому обмен идёт через
маленький **реестр**, к которому устройства ходят сами — соединения всегда
исходящие, значит сеть любая. Схема и ограничения — `docs/SYNC.md`.

### Сервер

- реестр общей библиотеки: `POST/GET /api/library`,
  `PUT/GET/DELETE /api/library/:id/file`, `GET /api/library/devices`
  (`services/api/src/library.js`, миграция `014-library`);
- метаданные и файл разделены: трек без файла виден с пометкой «недоступен»,
  вместо молчащего списка;
- `updatedAt` берётся с устройства — иначе каждая синхронизация перетирала бы
  правки других;
- файл кладётся один раз, читается потоком (без `readFile` в память), отдаётся с
  поддержкой `Range` — без неё не работает перемотка;
- доступ только по токену владельца: это личная библиотека, а не каталог в Wi-Fi;
- `services/api/test/library.test.js` — 5 сценариев: два устройства друг друга
  видят, файл скачивается целиком и по Range, multipart с телефона, 401 без
  токена, битые записи не валят синхронизацию.

### Приложение (mobile 0.8.0)

- **Лента** — первый экран: треки всех ваших устройств, у каждого подписано, чьё
  оно; свои играют локально, чужие скачиваются по нажатию и дальше играют без сети;
- вкладка **«На телефоне»** — то, что доступно без сети;
- настройки: **имя устройства** — так вас видно в ленте; адрес реестра берётся
  из уже подключённого сервера и при необходимости переопределяется вручную;
- статус синхронизации виден в шапке: «Ждём другие устройства», «Нет связи —
  показываем последнее известное», «Синхронизация не настроена»;
- кэш реестра на устройстве: без интернета лента показывает последнее известное
  состояние, а не пустоту;
- меню трека системное — его не срезает край списка (та же ошибка, что была в вебе).

### Поймано тестами

- в серверной загрузке файла одна ветка теряла имя параметра: любая загрузка
  отвечала `400 upload_failed`. Поймал интеграционный тест, не пользователь;
- `downloadUrl` для чужого трека сначала указывал на телефон — в мобильной сети
  это нерабочая ссылка; теперь файл всегда идёт из реестра.

## 0.27.0 — 2026-11-12

**Плеер больше не требует сервера.** Главная претензия к мобильному приложению была
не про баг: на первом экране просили «адрес сервера» и пароль, а без запущенного
Node-сервера приложение показывало `Network request failed`. Так устроен был весь
продукт — телефон считался тонким клиентом, и это неправильно для плеера.

- **Библиотека живёт на телефоне.** Новый слой `apps/mobile/src/local.tsx` +
  чистое ядро `src/lib/local.ts`: файлы, метаданные, плейлисты и статистика в
  хранилище устройства. Приложение открывается сразу в библиотеку — без входа,
  без адреса, без сети.
- **Импорт файлов с телефона**: `＋` → «Файлы с телефона» (системный выбор,
  несколько файлов сразу). Повторный импорт той же папки не задваивает треки:
  id считается от пути, дата первого добавления не перезаписывается.
- **Добавление по ссылке**: `＋` → «По ссылке». Прямой аудиофайл скачивается в
  папку приложения; HTML-страница открывается в `WebView` с перехватчиком
  (смотрит `fetch`/`XHR` и медиа-элементы), найденные адреса показываются
  списком. Платные подписки и защиту от скачивания приложение не обходит.
- **Сервер — необязательный источник**, а не вход: экран `ServerScreen`
  открывается из «Добавить музыку» → «Домашний сервер (необязательно)».
  Ошибка соединения больше не блокирует приложение: локальная музыка играет.
- **Статистика на телефоне**: `StatsScreen` — минуты за неделю и топ треков.
  Считается реально прослушанное время (приращение позиции), а не длительность
  трека: включённый на секунду трек не попадает в «прослушано целиком».
- **Плеер**: порядок источников — файл на телефоне → офлайн-копия → поток с
  сервера. Локальные треки играют в самолёте и без сервера.
- Меню трека — системное (`Alert`), а не самодельный слой: его нельзя обрезать
  `overflow` списка (та же ошибка, что была в вебе с меню «⋯»).
- Тесты: `local.test.ts` (9), `link.test.ts` (3). `npm run test:local` — 138/138.

Две поломки, найденные на телефоне после релиза. Обе — «работает на компьютере,
не работает в руках».

- **Меню действий с треком не открывалось** (кнопка «⋯»). Меню рисовалось

  повреждён)». Причина не в загрузке: `tauri android build --apk` собирает
  release-APK, а release без `signingConfig` остаётся неподписанным. Добавлен
  `scripts/android-sign-console.mjs` (тот же ключ `vision-release.p12`, что у
  плеера, версия и versionCode из CI), а в `console.yml` — проверка
  `apksigner verify`/`aapt2 dump badging`: сборка с неподписанным APK теперь
  падает в CI, а не на телефоне.
- В релиз админки вместо `app-universal-release-unsigned.apk` кладутся
  `VisionServer-<версия>-android.apk`, `.sha256` и постоянная ссылка
  `VisionServer-latest.apk`.
- `docs/ANDROID.md`: раздел про второй APK, подпись и ограничение —
  приложение открывает панель, но не запускает Node внутри телефона (сервер в
  Termux).

## 0.26.1 — 2026-11-11

Исправлен баг, который нашёлся на телефоне сразу после релиза.

- **Полноэкранный плеер не раскрывался** в браузерной версии: он поднимался
  снизу, но оставался приклеенным к нижней панели и обрезался по её высоте.

- Теперь `NowPlaying` рендерится **порталом в `document.body`**; в CSS панели
  добавлено объяснение, почему оверлеи нельзя вкладывать внутрь неё.
- Регрессию ловит `apps/web/src/now-playing.test.ts` (3 проверки): он падает,
  если из компонента убрать портал или если панель снова станет containing block.
- Мобильное приложение проверено отдельно: там полный плеер — нативный RN `Modal`,
  он рисуется поверх всего окна и контейнером списка не обрезается.

## 0.26.0 — 2026-11-11

Фаза 3 **закрыта**: последний её пункт — отчёты о падениях (H5). Теперь, если приложение
упало на телефоне или в браузере, это видно в панели, а не только в чужом сообщении
«у меня не открывается».

- **Приём отчётов** `POST /api/crashes` — **без токена**. Это осознанно: приложение падает
  и до входа, и после истечения сессии, и отчёт об этом падении нужнее всего. Защита —
  размер (16 КБ → `413 too_large`), JSON (иначе `400 invalid_json`) и частота
  (`429 rate_limited`, 60 *разных* падений в час на установку).
- **Схлопывание по fingerprint** (`name:message:первый кадр`): тысяча повторов одного
  бага — одна запись со счётчиком `count`, а не тысяча строк. Из кадра вырезается путь
  (`file:///data/.../player.tsx:245` → `player.tsx:245`), поэтому обновление приложения
  не плодит новые группы.
- **Лимит частоты считает только разные падения**: сломанный цикл в рендере не должен
  съедать квоту и заглушать следующее, новое падение (нашлось живой проверкой: 17
  повторов + 60 уникальных → отказ, хотя должен был записаться 61-й).
- **Клиенты**: мобильный ловит `ErrorUtils.setGlobalHandler` и `unhandledrejection`,
  веб — `window.onerror` и `unhandledrejection`; версия сборки подставляется Vite
  (`__APP_VERSION__`). Общая логика — `createCrashReporter` в `packages/shared`:
  очередь до 5 отчётов, повторы схлопываются, `5xx`/сеть ждут, `4xx` выбрасываются,
  `429` не повторяется. Ошибки внутри репортера гасятся — он не имеет права уронить
  приложение.
- **Панель**: раздел «Падения» в веб-клиенте (`#/crashes`) и вкладка в приложении
  запуска/админки — сводка за 7 дней (события, группы, установки), разбивка по
  приложениям и версиям, лента с раскрывающимся стеком и кнопкой чистки.
- **Чистка** `DELETE /api/crashes?keepDays=90` с записью в журнал (`crashes.prune`);
  хранение по умолчанию 90 дней.
- **Никаких адресов**: в отчёте только идентификатор установки (тот же, что у трекера
  реплик) и хеш адреса в журнале сервера. Нативные падения (NDK/Swift) не ловятся —
  для этого нужен Crashlytics, и это сознательно не делаем.
- OpenAPI (`CrashReport`, `CrashItem`, `/crashes`, `/crashes/summary`), `docs/API.md`,
  16 юнит+API тестов, 7 тестов репортера.

## 0.25.0 — 2026-11-11

Фаза 3, шаг H4: **загрузка с телефона**. Сценарий «записал — залил», без похода к
компьютеру. Заодно сервер научился принимать тело, которое присылает React Native.

- **Экран «Загрузить с телефона»** (`＋` в шапке библиотеки): выбор нескольких файлов,
  название/исполнитель/жанр прямо по очереди, прогресс каждого файла по процентам,
  ограничение 20 файлов за раз (десять параллельных загрузок на мобильной сети — это
  десять обрывов, поэтому очередь последовательная).
- **Файл не читается в память**: он уходит с диска через `FormData`, и 300-МБ запись
  не превращается в OOM. Для этого сервер принимает **multipart** (`services/api/src/multipart.js`):
  потоковый однопроходный разбор без зависимостей, первая часть отдаётся как обычный
  поток байтов, поэтому у загрузки осталась одна реализация. Тело-файл (веб) работает
  как раньше — контракт не сломан.
- **Метаданные до сети** (`apps/mobile/src/lib/upload.ts`): тип по расширению (Android
  регулярно присылает `audio/mpeg` для m4a), проверка размера и формата с теми же
  кодами, что у сервера, разбор «Artist - Title.mp3» из имени файла и подсказка для
  диктофона (`REC_20261111_1930.m4a`). Теги из самого файла по-прежнему читает сервер —
  телефону не нужно уметь разбирать ID3.
- **`content://` — не имя файла**: Android отдаёт такой uri без имени, и без проверки
  `title` превращался бы в «42». Это и ещё одно (врущий mime) найдено тестами логики
  до запуска на устройстве.
- **Дубликат — не ошибка**: повтор файла с другого устройства даёт «уже в библиотеке:
  <название>», а не красную плашку: `409 duplicate` разбирается в отдельный результат.
- **Зависимость**: `expo-document-picker@~14.0.8` (выбор файлов; без неё загрузка с
  телефона требует доступа ко всему хранилищу).
- Тесты: 8 на чистую логику (`apps/mobile/src/lib/upload.test.ts`, вошёл в `test:local`)
  и 10 на API (`services/api/test/multipart.test.js`: разбор на чанках от 1 байта,
  CRLF внутри файла, обрезанное тело, живая загрузка с телефона и веба, 409, 415, 401).
  Счёт: 170 контрактных, 112 клиентских, 14 скриптовых.

## 0.24.0 — 2026-11-11

Фаза 5, шаг D5 (P0): **резервное копирование с проверкой восстановления**. Раньше был
скрипт для cron, который никто не запускал; теперь копию можно снять из приложения,
она проверяется сразу и о состоянии копий знает панель.

- **`POST /api/backups`** — копия в один запрос: снимок базы через `VACUUM INTO` (живую
  базу не останавливаем, середину транзакции не ловим), `media/`, `covers/`,
  `manifest.json`, `.tar.gz`, ротация 14 последних.
- **Проверка встроена в создание**: `PRAGMA integrity_check`, число треков против
  живой библиотеки, наличие файла для каждого трека. Красный результат — `ok: false` в
  ответе, а не молчание: архив при этом **не** удаляется, разбираться нужен сам файл.
- **`POST /api/backups/verify`** — проверить восстановление из готового архива:
  распаковка во временный каталог и те же проверки. Архив мог побиться при копировании

## 0.17.0 — 2026-11-11

Фаза 6, шаг 5 (G10): **журнал действий**. Вопрос «кто удалил трек и почему ссылка
открывалась в четыре утра» теперь решается за пару секунд в панели, а не чтением

### Модель (`docs/API.md`, раздел «Аудит действий»)

- Таблица `audit_log` (миграция `010-audit-log`): время, актор (`owner`/`guest`/`system`),
  действие, цель, `share_id`, `ip_hash`, `request_id`, `details` (JSON ≤ 2 КБ).
- **Без PII и секретов**: адрес — `sha256(VISION_SECRET + ip)` (тот же хеш, что в
  `share_hits`), токен ссылки не пишется никогда; в журнале только `share_id`.
- **Сопоставимо с ответом**: `request_id` совпадает с `X-Request-Id`, поэтому «странный
  ответ» и строка журнала находят друг друга.
- **Гостевые визиты схлопываются**: повторное открытие той же ссылки с того же адреса
  за 10 минут не создаёт строку, а увеличивает `details.repeat` — журнал отвечает на
  вопрос, а не перечисляет обновления страницы.
- **Ретеншен**: `AUDIT_RETENTION_DAYS` (180 по умолчанию), чистка на старте и вручную;
  `AUDIT_ENABLED=0` выключает запись, чтение остаётся. Ошибка записи не ломает действие.

### Виджет `/embed/:token`

- **Своя оболочка, тот же источник**: компактная вёрстка без JavaScript и бандла,
  один `<audio>` (трек или первый трек плейлиста) плюс список остальных треков.

  в «второе приложение».
- **Встраивается**: `frame-ancestors *` и отсутствие `X-Frame-Options`; при этом
  `Referrer-Policy: no-referrer` (токен не утечёт в логи чужого сайта), `noindex`,

  вставка в популярный блог закрыла бы ссылку. Прослушивания идут гостевым маршрутом
  `/s/:token/stream/:id` и в статистике ссылки видны как обычно.
- Отозванная/истёкшая ссылка даёт короткую страницу-заглушку (`410`), битый токен — `404`.

### oEmbed

- `GET /api/oembed?url=&format=json|xml&maxwidth=&maxheight=` (и `/api/v1/oembed`):
  `version`, `type: rich`, `provider_name/url`, `title`, `author_name`, `thumbnail_*`,
  `html` (готовый `<iframe>`), `width`/`height`, блок `vision` (вид, число треков, длительность).
- Принимаются только наши адреса (`/s/<токен>`, `/embed/<токен>`, с хвостовым слэшем) —
  чужой `url` отклоняется `400 invalid_url`, чтобы эндпоинт не стал открытым прокси.

- `maxwidth`/`maxheight` (40…960) уменьшают iframe пропорционально: 480×180 для трека,

### Модель (`docs/adr/0008-timecode-comments.md`)

- **`share_comments`** (миграция `009-share-comments`): `share_id + track_id + at_seconds`,
  тело ≤ 600 символов, имя ≤ 40, `deleted_at` для мягкого удаления.
- **Изоляция по ссылке**: ключ ленты — пара «ссылка + трек». Глобального треда трека нет:
  иначе ссылка «для мамы» показывала бы переписку «для коллег». Продолжение модели ADR 0007.
- **Приватность**: `author` — свободное имя гостя, `author_hash = sha256(secret + IP)` нужен
  только для «своих» комментариев и троттлинга; сырого IP нет ни в БД, ни в логах.

- **Валидация на сервере**: `at` клампится в `0..duration` (если длительность известна),
  управляющие символы вырезаются, HTML экранируется при рендере; не больше 8 комментариев
  в минуту с адреса по одной ссылке (`429 too_many`).
- **Права**: удалить может автор (по хешу адреса) или владелец библиотеки. Чужой гость
  получает `403`, повторное удаление — `404`, без подсказок «был ли комментарий».

- `GET/POST/DELETE /api/shares/:id/comments` — владелец: лента (включая удалённые),

- `GET/POST /s/:token/comments`, `DELETE /s/:token/comments/:commentId` — гость по токену;
  для гостя отозванная ссылка отдаёт `410` **JSON** (`revoked|rotated|expired|exhausted`).
- **Без JavaScript**: лента рендерится сервером, форма — обычный `POST` с `303` обратно на

- CSP гостевой страницы расширена точечно: `script-src 'unsafe-inline'` и

- Метрика `vision_share_comment_total`; удаление ссылки с `?purge=1` уносит и комментарии.

### Приватные ссылки (E1) — `docs/adr/0007-private-links.md`

- **Модель**: `shares` + `share_hits` (миграция `008-shares`). В базе лежит

  Перевыпуск сохраняет старый хеш в `prev_token_hash`, поэтому старая ссылка отвечает

- **API**: `POST /api/shares` (targetKind, targetId, title, ttl, maxPlays),

- **Гостевой доступ** (`/s/*`, без сессии и без токена): страница, `stream` с Range

  невозможен по построению.
- **Лимит открытий** считает показы страницы; Range-запросы и скачивания пишутся только
  в журнал — браузер с десятком запросов не съедает лимит и не раздувает статистику.
- **Приватность гостя**: `share_hits` хранит `sha256(secret + ip)`, а не IP; владелец
  видит «сколько разных людей открыло», PII в БД и логах нет.
- **Токен не течёт**: структурные логи пишут `/s/:token/...` вместо реального токена

- Метрики: `vision_share_created_total{kind}`, `vision_share_open_total{kind}`,

## 0.10.1 — 2026-11-09

Офлайн-копии адресуются содержимым, а не строкой трека. Продолжение этапа 3: клиенты
и сервер понимают «файл» одинаково — по `sha256`.

### Что изменилось

- **Веб (`apps/web/src/offline.ts`)**: ключ копии в Cache Storage —
  `/__vision-offline/<checksum>` (у треков без `checksum` остаётся `/__vision-offline/<id>`).
  Индекс `vision.offline.index` получил поле `hash`, а поиск идёт по любому из двух
  ключей: `id` или `sha256`. Один файл, импортированный заново под новым `id`, не
  качается второй раз; удаление и воспроизведение находят копию по обоим ключам.
  Новые хелперы `offlineRef(track)` (ключ копии), `isTrackCached`, `offlinePlayable`,
  `removeTrackCopy` — компоненты работают с треком, а не с сырыми ключами.
- **Совместимость**: копия, скачанная до появления трекера (ключ `/__vision-offline/<id>`),
  по-прежнему находится по `checksum`; повторное скачивание переводит её на контентный
  ключ и удаляет старую запись из Cache Storage.
- **Веб-вызовы**: `TrackList`, `state/player.tsx`, `App.tsx`/`seeds.ts` (`syncReplicas`)
  работают через `isTrackCached` / `offlinePlayable` / `removeTrackCopy`, а не с `track.id`.
- **Телефон (`apps/mobile/src/downloads.tsx`)**: индекс копий ищет запись по `id` или
  по `hash` (`apps/mobile/src/lib/downloads.ts`, чистая функция `findCopy`); повторное
  скачивание того же содержимого пропускается, удаление работает по любому ключу.
  Имена файлов не меняются — старые загрузки и записи без `hash` продолжают работать.
- Совместимость: старый индекс без `hash` читается как раньше, переиндексация не нужна.

- **`FFMPEG_THREADS`** — ограничение потоков ffmpeg (полезно и на слабых серверах).

- **`docs/TERMUX.md`** — установка, доступ по Wi-Fi, HTTPS через Tailscale/Cloudflare

- 4 юнит-теста на резолв ffmpeg: приоритет `FFMPEG_PATH`, пропуск нерабочего
  бинарника, полное отсутствие ffmpeg, Android-профиль потоков.

## 0.6.0 — 2026-11-09

Фаза 2 «Аудио 2.0»: лёгкий поток, ровная громкость, HLS и прогрев следующего трека.

### Добавлено

- **Фоновый транскодинг** (`services/api/src/transcode.js`): после загрузки трек
  попадает в очередь и перекодируется в **opus 96 kbps** и **aac 128 kbps**, плюс
  **HLS-нарезка** по 6 секунд. Очередь последовательная, ответ клиенту ffmpeg не ждёт.
- **Нормализация −14 LUFS** (`loudnorm=I=-14:TP=-1.5:LRA=11`) при каждом варианте —
  треки из разных источников звучат на одном уровне.
- **`GET /api/tracks/:id/stream?format=opus|aac`** — отдача варианта с Range; если его
  ещё нет, сервер прозрачно отдаёт оригинал (`X-Variant-Fallback`).
- **HLS**: `GET /api/tracks/:id/hls.m3u8` и `GET /api/tracks/:id/hls/:segment`.
  Сегменты в плейлисте переписаны в абсолютные пути с той же HMAC-подписью, поэтому
  относительное разрешение URL не ломает авторизацию.
- **`GET /api/media`** теперь отдаёт `streams: { original, opus, aac }` и `hls`;
  `GET /api/tracks/:id` — список готовых `variants`.
- **Выбор кодека на клиенте** через `canPlayType()`: opus → aac → оригинал, а в Safari
  с нативным HLS — плейлист.
- **Prefetch следующего трека**: подписанная ссылка запрашивается заранее, первые
  256 КБ уходят в HTTP-кэш браузера — переключение почти без буферизации.
- **320 пиков вместо 180** + сглаживание волны (среднее по окну и 3-точечный фильтр),
  чтобы не было «дребезга» на тихих участках.
- Метрики `vision_transcode_total{result}` и `vision_transcode_seconds_total{kind}`;
  `/api/health` показывает `ffmpeg` и `transcode`.
- `TRANSCODE_BACKFILL=1` — при старте догоняет треки, загруженные до появления ffmpeg.

### Важно

- **Без ffmpeg сервис работает как раньше**: оригиналы, без вариантов и HLS.
  Бинарник ищется в `FFMPEG_PATH` → `ffmpeg-static` → `PATH`; в Docker-образ
  добавлен `apk add ffmpeg`.
- `ffmpeg-static` подключён в `optionalDependencies`: если бинарник не скачался
  (нет сети/неподходящая платформа), `npm install` не падает.
- Осталось на потом: MSE-плеер для HLS в Chrome/Firefox (сейчас HLS играет в Safari),
  gapless/кроссфейд, кэш медиа в Cache Storage.
