# План внутренней технической alpha Vision v2

**Статус:** подготовка; alpha не запущена, v2 EXE не собраны.
**Тип этапа:** закрытая техническая alpha команды/владельца, не внешняя invite-only бета.
**Целевая топология:** один серверный ПК и клиентские ПК; переносить БД, API и storage на отдельные машины не планируется.
**Целевые артефакты:** Windows 10/11 x64 server setup `.exe` и отдельный client `.exe` для v2; цель и сроки — после Stack Ready, см. [`ADR-0022`](adr/0022-v2-windows-alpha-installers.md).
**Клиент:** v2 web UI для артиста/слушателя, radio/recsys, упакованный в client `.exe`; старый desktop-плеер не подходит.
**Гейт разработки:** владелец подтвердил строгое следование ADR-0021: новые продуктовые web/client-фичи и сборка client `.exe` только после полного Stack Ready и его явной приёмки.
**Сеть:** LAN или частная VPN пока не выбраны. До отдельного плана не менять сетевые привязки, Windows Firewall и роутер.

> Этот план не разрешает публичный запуск, внешние приглашения или публичные загрузки. Существующий `compose.platform.local.yml` остаётся loopback-only backend smoke. Не открывайте его порты клиентским ПК и не выставляйте API/MinIO в интернет.

## 1. Цель и границы

Проверить после прохождения гейтов, что один серверный компьютер обслуживает с клиентских ПК v2-сценарии артиста и слушателя через отдельный Windows client `.exe`: каталог и воспроизведение разрешённых тестовых треков, отправку артистом тестового трека в закрытый ingest/moderation-процесс, radio session/schedule, последовательность воспроизведения, рекомендации, skip и feedback.

В alpha включаются только материалы, на которые владелец теста имеет подтверждённые права. До решения по live TTS и редакционному контенту базовый radio-сценарий — музыка и рекомендации; новости, погода, реклама и production TTS не включаются. Это не меняет требований ADR-0021 к backend radio/voice acceptance tests и fake provider в CI.

**Не входит:** внешняя когорта 10 артистов + 50 слушателей из [`BETA-PLAN.md`](BETA-PLAN.md), открытая регистрация, публичное распространение UGC, реклама/монетизация, мобильные/native-клиенты, разнос компонентов по нескольким серверам и переключение legacy SQLite-продукта на v2.

### Целевые Windows EXE после Stack Ready

- **Server setup `.exe`:** установщик/менеджер v2 для одного сервера Windows. Это не один самодостаточный бинарник API: v2 зависит от PostgreSQL/pgvector, Redis, private S3-compatible storage, API и worker. Существующий Docker Compose + Docker Desktop/WSL2 — предварительная основа, не утверждённая схема упаковки. Перед кодом отдельный packaging ADR должен определить prerequisites, автозапуск/service lifecycle, secrets, data volumes, backup/restore, update/uninstall и сетевые правила.
- **Client `.exe`:** Windows-клиент, содержащий v2 web UI и сценарии артиста/слушателя/radio/recsys. Точный Tauri/WebView wrapper и настройка серверного origin выбираются после Stack Ready. Нельзя захардкодить `localhost` для сервера, который работает на другом ПК.
- **Не использовать как v2 артефакты без переработки:** `apps/console` упаковывает legacy SQLite API, а `apps/desktop` — старый плеер личной библиотеки. Они не подключены к v2 API; Windows-сборки заморожены и не прошли целевую установку/runtime-проверку.
- Артефакты alpha — только для закрытой внутренней выдачи. Не публиковать их как релиз и не открывать Firewall/роутер автоматически. Клиентский доступ разрешать только после выбора LAN/VPN и проверки TLS и signed media URL.

Участники alpha — только владелец и заранее допущенные внутренние тестировщики. До появления проверенной процедуры приглашения, email confirmation и rate limits предпочтительны заранее созданные тестовые учётные записи; не включать открытую регистрацию. Внутреннее решение модерации тестовых материалов может выполняться уполномоченным оператором через проверенный API/runbook; moderator UI не является частью выбранных пользовательских сценариев.

## 2. Этапы и гейты

### Этап 0 — зафиксировать scope (выполнено)

- [x] Только внутренняя техническая alpha; внешний набор не начинать.
- [x] Один серверный ПК + клиентские ПК; web, сценарии артиста/слушателя.
- [x] Включить radio/recsys в пользовательскую проверку.
- [x] Сохранить строгий ADR-0021: сначала полный Stack Ready, затем web/client-фичи и сборка client `.exe`.
- [x] Зафиксировать цель: v2 server setup `.exe` + client `.exe` после Stack Ready; legacy EXE не использовать как v2.
- [ ] Выбрать LAN или VPN; сетевой дизайн остаётся открытым.
- [ ] Принять technical packaging ADR (Compose vs Windows service, installer lifecycle, signing) до реализации server installer/client wrapper.

### Этап 1 — текущий локальный backend smoke (частично проверен)

В этой рабочей среде прошли `npm run test:all`, `npm run typecheck:api`, `npm run check:api-types` и `npm run build`. Это проверки кода и существующего приложения; они **не** доказывают Stack Ready, работу Docker на целевом Windows-ПК, клиентский сетевой доступ или продуктовый v2 web E2E. `npm run build` собирает существующий `apps/web`, который пока не является v2 UI.

Следующее подтверждение этого этапа — отдельный owner-run Windows/Docker Desktop smoke по [`BETA-WINDOWS-LOCAL.md`](BETA-WINDOWS-LOCAL.md): запуск API/worker/PostgreSQL/Redis/private S3, health и пустой каталог, повторный запуск, остановка/восстановление и проверка backup/restore. Порты остаются на loopback. Этот smoke не требует и не разрешает клиентский LAN-доступ.

### Этап 2 — закрыть Stack Ready до любых новых app-фич

Сверяться с полным списком [`ADR-0021`](adr/0021-backend-first-before-apps.md) и [`ROADMAP-v2.md` §17.4](ROADMAP-v2.md). В частности, нужны проверяемые доказательства для:

- API F1–F3, контрактов, разрешений и negative/security tests;
- чистой и upgrade-миграции PostgreSQL, SQLite-совместимости, backup/restore и rollback rehearsal на копии данных;
- приватных storage URL, подписанных URL, takedown и invalidation;
- queue/worker retry, дубликатов, idempotency, DLQ и восстановления после рестарта;
- закрытого ingest → moderation → публикация; неподтверждённый fingerprint не считается `clear`;
- events/recsys: privacy rules, контрольных профилей и измеримых offline metrics;
- radio/voice integration tests, принятого сценария и cost accounting;
- staging/deploy, наблюдаемости, alarms, security review и проверенных operator runbooks/restore.

По roadmap этот gate **не принят**: есть существенная backend-реализация и hosted CI evidence, но открыты Windows/операционная приёмка, restore/rollback, rate limits/anti-fraud, часть recsys/radio acceptance и staging/observability. Зелёные тесты этого прохода не закрывают эти пункты. Только владелец принимает Stack Ready; наличие модулей или CI само по себе не является приёмкой.

### Этап 3 — спроектировать безопасный доступ с клиентских ПК (можно параллельно с этапом 2)

Сначала сравнить два допустимых варианта; ничего не открывать, пока владелец не выберет вариант и план не пройдёт review.

| Вариант | Подходит, если | Что потребуется |
|---|---|---|
| Закрытая LAN | сервер и все клиентские ПК находятся в одной контролируемой сети | выделенная/доверенная сеть теста, локальное имя сервера, доверенный TLS-сертификат, firewall allowlist только клиентской подсети/устройств |
| Частная VPN/overlay | клиенты находятся в разных сетях или LAN недоверенная | управляемые ключи устройств, частный DNS/маршрут и TLS; отдельно проверить зависимость от VPN endpoint/relay |

Для обоих вариантов целевое ограничение — один защищённый HTTPS entry point для client `.exe` (и browser-доступа, если он сохраняется) через reverse proxy. Не публиковать PostgreSQL, Redis, API или MinIO напрямую на клиентские/публичные интерфейсы; не делать router port-forward. Открытый порт, если он понадобится после review, должен вести только на reverse proxy и быть ограничен участниками теста.

Отдельно проверить storage-путь: браузеры получают подписанные URL, поэтому `PLATFORM_S3_PUBLIC_ENDPOINT` должен указывать на адрес, достижимый клиентскими ПК, а не на `127.0.0.1`. Для него потребуются HTTPS, точный CORS allowlist для web origin и end-to-end проверки подписи/Host/path, presigned PUT/GET и audio Range. Текущая конфигурация MinIO и storage endpoint рассчитана на локальный smoke, а не на такую схему. Одной смены `PLATFORM_HOST` недостаточно.

**Предварительная рекомендация, не принятое решение:** если все ПК действительно находятся в одной доверенной сети, начать с LAN-only reverse proxy и TLS; если есть удалённые/недоверенные клиентские сети — сравнить с private VPN. Сначала уточнить фактическую сеть, сертификаты и локальный DNS; до этого ни Compose, ни firewall не менять.

### Этап 4 — v2 web UI и Windows EXE после явной приёмки Stack Ready

Только после этапа 2 подключать `apps/web` к v2 API и делать минимальные экраны/потоки. Затем, по отдельному packaging ADR, собрать v2 server setup `.exe` и упаковать тот же v2 UI в client `.exe`. Не собирать legacy `apps/console`/`apps/desktop` как замену этим артефактам.

1. **Артист:** вход, профиль и подтверждение прав для тестового материала; загрузка в private quarantine; отображение статуса ingest/moderation; публикация только после разрешённого внутреннего решения.
2. **Слушатель:** вход, каталог/поиск, карточка и воспроизведение только опубликованного тестового трека.
3. **Радио/recsys:** запуск сессии, получение расписания, последовательное воспроизведение сегментов, переход к следующему треку, skip и feedback; проверить, что рекомендации используют тестовый профиль и объяснения/статусы не вводят в заблуждение.
4. **Отказы:** просроченный токен/URL, неизвестный или quarantine-трек, чужой объект, недоступный storage/API, повтор события и потеря сети; приватный контент остаётся закрытым.

Выполнить E2E установленного client `.exe` на реальных клиентских ПК через выбранный защищённый server origin; если сохраняется прямой browser-доступ, отдельно проверить и его. Ни текущий legacy web, ни API smoke не заменяют эти проверки. Не включать регистрацию/загрузки в работающем контуре одним флагом без тестов доступа, квот, rate limits и закрытой модерации.

### Этап 5 — rehearsal и закрытая внутренняя alpha

Входные условия:

- [ ] Stack Ready принят владельцем; новая web-часть и client `.exe` приняты отдельным E2E.
- [ ] Владелец выбрал LAN/VPN; TLS, DNS, firewall и client-to-storage flow проверены с клиентских ПК.
- [ ] Server setup `.exe` установлен и проверен на чистом Windows 10/11 x64; lifecycle и uninstall протестированы.
- [ ] Backup/restore и rollback повторно проверены на целевом серверном ПК.
- [ ] Есть только заранее допущенные тестовые учётные записи и контент с подтверждёнными правами.
- [ ] Регистрация, uploads, доступ и media URLs ограничены конфигурацией alpha; ни один внутренний сервис не доступен из публичного интернета.
- [ ] Есть владелец инцидентов и процедура остановки/отзыва доступа.

Проводить тесты сначала на пустом/синтетическом каталоге, затем на разрешённых тестовых треках. Не собирать персональные данные в GitHub Issues/PR и не использовать production-аккаунты/секреты. Результат — фактическая матрица сценариев, дефекты, журнал решений и go/no-go по следующему этапу. Внешних участников на этом этапе нет.

## 3. Критерии остановки alpha

Немедленно остановить доступ и вернуться к loopback-only, если обнаружен любой из пунктов:

- API/MinIO/DB/Redis достижимы с неразрешённого устройства или из интернета;
- signed media URL не ограничен/не истекает, quarantine-файл виден слушателю или чужой пользователь получает доступ к объекту;
- неподтверждённый трек становится доступен до moderation decision;
- теряются данные/события, restore не проходит, секрет попал в логи/репозиторий;
- нет ответственного за инцидент, takedown или отзыв учётной записи.

**Успешное прохождение внутренней alpha не означает внешнюю бету.** Юридические, privacy/consent, права, feedback, cohort и публичного доступа гейты из [`BETA-PLAN.md`](BETA-PLAN.md) остаются отдельными.

## 4. Открытые решения

1. LAN-only или private VPN/overlay — зависит от расположения и доверия к клиентским ПК.
2. Локальный DNS и способ доставки доверенного TLS-сертификата на тестовые ПК.
3. Server installer: Compose/orchestrator или Windows service, prerequisites, автозапуск, обновление и удаление — отдельный packaging ADR; требования ADR-0020 разрешить для v2 явно.
4. Client `.exe`: точный Tauri/WebView wrapper, подпись и внутренний канал выдачи.
5. Radio alpha ограничивается музыкой/recsys или отдельно включает голосовой TTS; production provider и права/стоимость не выбраны.
6. Конкретный состав внутренних тестировщиков и способ выдачи заранее созданных аккаунтов.

До принятия этих решений этапы упаковки, развёртывания и клиентского доступа не начинаются.
