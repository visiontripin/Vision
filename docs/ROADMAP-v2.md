| Метка | Значение |
|---|---|
| `- [ ]` | задача не принята; отметка сама по себе не говорит, начиналась ли реализация |

Правила:

1. Каждая задача имеет владельца (код роли из §4), приоритет (`P0` — без неё фаза не закрывается, `P1` — важно, `P2` — можно вырезать) и грубую оценку в днях.
2. Вырезая задачу — не удаляйте строку, ставьте `[-]` и причину. Так видно, что было решено не делать, и агент не вернёт это обратно.
3. Добавляя задачу — дописывайте в конец фазы с новым суффиксом (`Ф3.14`, `Ф3.15`), не перенумеровывая существующие.
4. Изменение контракта API (§7) или модели данных (§6) — сначала правка этого документа, потом код. Спорное решение — ADR (§19.2).
5. Приоритеты фаз не меняются задним числом: если Ф3 «Моя волна» съезжает, вырезайте задачи внутри неё, а не переносите её после монетизации.

## 1. Видение

**Одной строкой:** живое персональное радио для независимых артистов — музыку ведут ведущие, а слушатель открывает для себя то, чего нет в больших каталогах.

**Формула позиционирования:** SoundCloud (UGC + сцена) × Моя волна (персональный поток) × AI-ведущие (живой эфир).

### 1.1 Что делает продукт живым

- Эфир **непредсказуем, но персонален**: следующий трек подбирается по вкусу, а подводка ведущего знает, что играло до этого.
- Между музыкальными блоками — **короткие вставки**: ведущий, викторина, лайфхак, погода, брейкньюз, джингл, реклама. Правило: **не больше 90 секунд подряд без музыки**.
- Слушатель **участвует**: отвечает на викторину прямо в плеере, ставит лайк, пишет комментарий к секунде, подписывается на артиста.
- Артист видит **обратную связь в цифрах**: дослушивания, скипы, рост аудитории, — и может купить промо или попасть в лейбл.

### 1.2 Персоны

| Персона | Контекст | Ключевая задача | Метрика успеха |
|---|---|---|---|
| **Слушатель** | Фон в дороге/работе, хочет открытия | Включил волну — не хочется переключать | Длина сессии, skip-rate, D7 |
| **Инди-артист** | Загрузил трек, ищет первых слушателей | Быстро получить честный фидбек и рост | Время до 100-го дослушивания |
| **A&R / лейбл** | Ищет, кого выпускать | Найти артиста с растущим удержанием | Точность скоринга, конверсия в контракт |
| **Рекламодатель** | Хочет аудиторию по вкусу/гео | Купить слоты и получить отчёт с маркировкой | eCPM, fill rate, отчётность |
| **Модератор** | Проверяет загрузки и жалобы | Быстро отсеять чужое/запрещённое | Время реакции, доля ошибок |

### 1.3 Северная звезда и контрметрики

- **North Star:** часы живого эфира на активного слушателя в неделю.
- **Контрметрики (не имеют права расти):** skip-rate после вставок, доля рекламы в эфире, время реакции на takedown, себестоимость часа эфира.

## 3. Pivot-решения

Эти решения принимаются **до** начала Ф1. Каждое оформляется отдельным ADR.

| ADR | Решение | Статус | Владелец |
|---|---|---|---|
| 0011 | **Pivot:** личный плеер → публичная UGC-платформа с радио. `PRODUCT.md` и промпты обновлены | принято владельцем как направление, запуск не одобрен | PO |
| 0012 | **Postgres + pgvector** как основное хранилище; SQLite остаётся только для локального режима | отдельный platform pool и migrations 001–008; PostgreSQL 16 + pgvector integration проходят в hosted CI; SQLite-миграция, production backup/restore и owner-run Windows rehearsal открыты | TL |
| 0013 | **S3-совместимое хранилище + CDN** для медиа; provider и бюджет не выбраны | принято как целевая архитектура, provider открыт | TL / OPS |
| 0014 | **Эфир как плейлист сегментов** (клиентский секвенсор), а не серверный live-mix на MVP | принято для MVP; server-side radio session/schedule APIs есть, client sequencer/player runtime не принят | TL / RADIO |
| 0015 | **Реплики-сиды для UGC:** только подтверждённый контент либо отключение; вариант требует решения владельца после консультации | proposed; не принято | SEC / LEGAL / PO |
| 0016 | **Заморозка платформ:** desktop, console, embedded Node-in-APK — эксперименты, развитие приостановлено до PMF | принято; код сохранён, workflow ручной/заморожен | PO |
| 0017 | **Модерация до публикации** (quarantine → fingerprint → очередь → publish) | политика принята; platform API покрывает submission, queue, approve/reject/escalate, claims и counter-notice; quarantine ingest/worker и PostgreSQL/Redis/S3 CI integration проходят. | 0018 | **Маркировка рекламы/промо**; рынок и применимые идентификаторы определит юрист | принято как safety-гейт; реклама выключена | LEGAL / ADTECH |
| 0019 | **Транспорт эфира:** progressive-секвенсор на MVP, HLS/MSE — Ф3.13, live-микс — после Ф5 | принято для целевого MVP; client playback/sequence runtime не реализован | TL |
| 0020 | **Windows Vision Server:** код сохранён, workflow временно заморожен; отдельное требование владельца конфликтует с freeze и остаётся открытым | не считать выполненным или отменённым | PO |

## 5. Целевая архитектура

### 5.1 Принципы

1. **Один контракт — много клиентов.** Типы и SDK живут в `packages/shared`, генерируются из OpenAPI.
2. **Разделение путей:** тяжёлое (транскодинг, фингерпринт, эмбеддинги, синтез речи) — в воркерах и очередях, никогда в HTTP-запросе.
3. **Эфир собирается заранее.** Планировщик отдаёт клиенту расписание сегментов на 10–15 минут вперёд; клиент играет их секвенсором. Серверный live-mix — позже.
4. **Приватность по умолчанию сохраняется** для личного режима, но публичный контур — отдельная зона с явным согласием на публикацию.
5. **Всё измеряемо.** Любая фича выходит с событием и дашбордом, иначе она не принята.

### 5.2 Компоненты

- `apps/web` — слушатель + кабинет артиста + модератор (React 19 + Vite)
- `apps/mobile` — Expo, заморожен до Ф5
- `apps/desktop` — Tauri, заморожен
- `apps/console` — админка заморожена, критичные функции переезжают в `web/admin`
- `packages/shared` — типы + SDK из OpenAPI
- `packages/ui` — (опционально) общие компоненты плеера
- `services/api` — HTTP: identity, catalog, shares, radio-api, ads-api, billing-api, admin
- `services/ingest` — воркер: transcode → fingerprint → moderation → embeddings → publish
- `services/radio` — планировщик эфира, сценарный движок, подбор вставок
- `services/recsys` — эмбеддинги, ANN, профиль вкуса, ранжирование
- `services/voice` — TTS-синтез, кэш реплик, микс/ducking-метаданные
- `services/events` — приём событий, дедуп, антифрод, запись в витрины
- `infra` — Postgres (+pgvector), Redis (очереди/лимиты/кэш), S3/MinIO, CDN, метрики

### 5.3 Технологический стек (целевой)

| Слой | Сейчас | Цель | Комментарий |
|---|---|---|---|
| БД | `node:sqlite` | **Postgres 16 + pgvector** | миграции нумерованные, SQLite — только local-mode |
| Хранилище | локальный диск | **S3/MinIO + CDN** | lifecycle: оригинал → cold, варианты → hot |
| Очереди | очередь в процессе | **Redis + воркеры** (BullMQ или своё на Redis) | ретраи, dead-letter, идемпотентность |
| Поиск | FTS5 | **Postgres FTS** (+ позже Meilisearch) | сохранить поведение префиксного поиска |
| Векторы | — | **pgvector** | 512-мерные эмбеддинги, ivfflat/hnsw |
| Эфир | — | секвенсор на клиенте + планировщик на сервере | ADR-0014 |
| HLS | сервер есть, клиента нет | **hls.js (MSE)** | Ф3.13 |
| TTS | — | облачный движок + локальный фолбэк | кэш по `hash(text+voice+params)` |
| Фингерпринт | — | внешний API (AudD/ACRCloud) + свой кэш | Ф1.5 |
| Типы API | JS | **JSDoc + checkJS**, далее TS | Ф0.7 |

### 5.4 Потоки данных

**Загрузка трека:**
client → `POST /api/v2/tracks` (multipart, quarantine) → ingest: magic bytes → sha256 → transcode (opus/aac) → loudnorm −14 LUFS → fingerprint → match? → moderation_queue / auto_reject → embeddings (CLAP/ONNX) → tags/mood → publish → catalog + CDN invalidation → событие `track.published`.

**Формирование волны:**
client → `POST /api/v2/radio/session` {mood, context} → recsys: candidates (ANN + tags + fresh + editorial + promo-slot) → ranking + diversity (MMR) → music blocks → radio: вставка host/quiz/lifehack/weather/news/jingle/ad по правилам частот → voice: TTS из кэша или синтез → S3 → ответ: schedule на 10–15 мин + mix-метаданные → client: секвенсор, crossfade, ducking, события play/skip/finish.

## 6. Модель данных

Ключевые таблицы (сокращённо, только новые/изменённые). Полная схема — в миграциях.

### 6.1 Пользователи и артисты

### 6.2 Каталог и права

## 8. Ядро рекомендаций

### 8.1 Сигналы

| Событие | Вес | Комментарий |
|---|---|---|
| `skip_early` (< 20 с) | −3 | главный негативный сигнал |
| `play_30s` | +1 | минимальный интерес |
| `finish` | +3 | дослушал |
| `repeat` | +4 | сильный позитив |
| `like` | +5 | явный сигнал |
| `add_playlist` / `share` | +6 | самый сильный |
| `follow_artist` | +8 | долгосрочный интерес |

Затухание: экспоненциальное, полураспад 30 дней. Антифрод: не более N событий одного типа на трек в час, отсечение ботов по энтропии сессии.

### 8.2 Пайплайн

1. **Эмбеддинги трека.** Аудио → CLAP/OpenL3-подобная модель (ONNX) → вектор 512. Дополнительно: авто-теги жанра и настроения. Считается в `ingest`, хранится в `pgvector`.
2. **Профиль вкуса.** Взвешенный центроид последних позитивных треков минус негативные; отдельно — веса жанров, настроений, аффинити к артистам, карта усталости.
3. **Кандидаты (300–500):** ANN по профилю (150) + жанр/настроение (100) + свежие публикации (80) + редакционные подборки (40) + промо-слот (≤ 30, помечен).
4. **Ранжирование:** `score = 0.40·similarity + 0.20·affinity + 0.15·freshness + 0.15·quality + 0.10·editorial − fatigue − diversity_penalty`. Промо **не меняет score** — оно занимает выделенный слот с жёстким капом (§12.1).
5. **Разнообразие (MMR):** не более 2 треков одного артиста в час, не более 3 подряд одного жанра, обязательная доля новинок ≥ 15%.
6. **Объяснимость:** каждый трек несёт `reason` — «похоже на X», «новый релиз артиста, которого вы слушаете», «промо».

### 8.3 Cold start

Онбординг: выбрать 5 жанров/настроений и 3–5 знакомых артистов → стартовый профиль. Первые 20 треков — исследовательский режим (больше свежого и разнообразного), затем переключение на эксплуатацию.

### 8.4 Оценка качества

- **Офлайн:** recall@50, nDCG@20 на отложенной неделе событий; порог — не хуже бейзлайна «популярное в жанре».
- **Онлайн:** A/B, главные метрики — skip-rate и длина сессии; контрметрики — доля новинок, покрытие каталога.
- **Целевые значения Ф2:** skip-rate < 25%, подборка < 300 мс p95, покрытие каталога > 80%, выигрыш над шаффлом ≥ 20% по skip-rate.

## 9. Движок эфира

### 9.1 Модель (ADR-0014)

MVP — **«плейлист-эфир»**: сервер отдаёт расписание сегментов, клиент играет их последовательно с кроссфейдом и ducking. Это даёт ощущение живого радио без дорогого серверного микса и работает на всех клиентах. Серверный live-микс (общие каналы, «эфир города») — после Ф5.

### 9.2 Типы сегментов

| Тип | Длительность | Источник | Частота по умолчанию |
|---|---|---|---|
| `music` | 2–5 мин | recsys | 3–5 треков подряд |
| `host_intro` | 8–15 с | TTS + шаблон | перед блоком, 1 из 2 блоков |
| `host_backsell` | 6–12 с | TTS + шаблон | после трека, 1 из 3 |
| `quiz` | 20–35 с | сценарий + TTS | 1 раз в 20–30 мин |
| `lifehack` | 20–30 с | контент-карточка + TTS | 1 раз в 30–40 мин |
| `weather` | 12–20 с | API + шаблон | 1 раз в 30 мин, если гео задано |
| `news` | 20–30 с | лента + факт-чек + TTS | 1 раз в час, только свежее 60 мин |
| `jingle` | 3–6 с | библиотека джинглов | между блоками |
| `ad` | 15–30 с | ad-server | ≤ 5% эфирного времени |
| `promo` | трек | promo-кампания | ≤ 1 на 10 треков, с пометкой |

### 9.3 Жёсткие правила планировщика

1. Не более 90 секунд подряд без музыки.
2. Не более одной «разговорной» вставки между двумя музыкальными блоками.
3. Две рекламы подряд запрещены; реклама не идёт первой в сессии.
4. Суммарная доля рекламы ≤ 5% времени сессии.
5. Промо-трек помечен в UI и в событиях; ≤ 1 на 10 треков; не более 2 от одного артиста в час.
6. Новости старше 60 минут не выходят; факт-чек обязателен.
7. Погода только при известном гео и только с актуальностью < 30 минут.
8. Frequency cap на пользователя: один и тот же креатив ≤ 3 раз в сутки.
9. Ночной режим (по локальному времени): без брейкньюз, тише джинглы.
10. Скип вставки → её тип временно понижается в частоте на 2 часа.
11. Пользователь может выключить любой тип вставок кроме обязательных юридических.
12. Всё в эфире нормализовано к −14 LUFS; речь микшируется с ducking −6 dB.

### 9.4 Алгоритм сборки блока

```
build_block(session, ahead_seconds = 900):
  block = []
  while sum(duration(block)) < ahead_seconds:
      tracks = recsys.next_tracks(session.user, count = 4)
      if block.should_open_with_host(prefs):
          block += voice.render(script('host_intro', context = prev_track, next = tracks[0]))
      block += tracks
      slot = scheduler.pick_insertion(session, prefs, counters)   # quiz|lifehack|weather|news|jingle|ad
      if slot and rules.allow(slot, block):
          block += render_segment(slot)
      if promo.due(session):
          block += promo.pick_track(session)                       # с пометкой
  return block.map(attach_mix_metadata)
```

### 9.5 Клиентский секвенсор

- Один аудио-элемент + предзагрузка следующего сегмента (первые 256 КБ).
- Кроссфейд 400–800 мс между музыкой; речь — поверх интро/аутро с ducking.
- Ответ на викторину — оверлей в плеере, не прерывает музыку.
- Скип сегмента отправляет `feedback` и пересобирает хвост расписания.
- Офлайн: эфир не работает, показывается честный баннер и предлагается скачанное.

## 10. Контентный слой

### 10.1 Ведущие

- **Два тембра** (например, «тёплый» и «энергичный»), чередование по времени суток.
- **Tone of voice:** коротко, по-человечески, без канцелярита и без «дорогие радиослушатели». Одна мысль на реплику.
- **Контекстность:** подводка знает предыдущий трек, время суток, город и погоду, имя артиста.
- **Произношение:** словарь имён артистов и названий треков (`pronunciation_dict`), пополняется артистом в кабинете.
- **Кэш:** `hash(text + voice + params)` → S3. Повторные подводки не синтезируются заново. Целевой hit-rate кэша > 60%.
- **Запреты:** не синтезировать непроверенные новости, не имитировать реальных людей, не озвучивать юридически значимые тексты без шаблона от LEGAL.

### 10.2 Викторины

- Формат: вопрос о только что игравшем треке/артисте или общий музыкальный вопрос.
- 3–4 варианта, ответ тапом в плеере, объяснение после ответа.
- Награды: бейджи, streak, влияние на профиль вкуса — **не** деньги на старте.
- Библиотека вопросов генерируется из метаданных каталога + редакционный набор; дубли отсекаются.

### 10.3 Лайфхаки, погода, брейкньюз

| Тип | Источник | Проверка | Актуальность |
|---|---|---|---|
| Лайфхак | редакционная библиотека + предложения пользователей | модерация TRUST | бессрочно |
| Погода | внешний API по гео пользователя | автоматическая | < 30 мин |
| Брейкньюз | RSS/лента партнёра | **обязательный факт-чек** редактором | < 60 мин |

Все карточки хранятся в `content_cards` с `valid_until` и `fact_checked`. Просроченное в эфир не попадает.

## 11. Права, модерация, безопасность

### 11.1 Публикация UGC

1. При загрузке артист подтверждает права (чекбокс + текст оферты, фиксируется `rights_confirmed_at` и версия оферты).
2. Трек уходит в `quarantine`, публично не виден.
3. Фингерпринт сверяется с базой; совпадение → `in_review` или авто-отклонение.
4. Модератор проверяет очередь: обложка, название, текст, семпл.
5. Публикация → `published`, попадает в каталог и в кандидаты рекомендаций.

### 11.2 Takedown

- Публичная форма жалобы → `rights_claims` с `sla_due_at = now + 24h`.
- Спорный контент скрывается до разбора (`taken_down`), заявитель и артист получают уведомления.
- Встречное уведомление (`counter_notice`) → повторное рассмотрение.
- Repeat-infringer policy: 3 подтверждённых нарушения → блокировка аккаунта.

### 11.3 Реклама и закон

- Каждый креатив имеет `erid` и привязку к договору в ОРД; без них кампания не активируется.
- Отчётность в ЕРИР — выгрузка из `ad_impressions` + `invoices`.
- Возрастные и гео-ограничения категорий — на уровне таргетинга.
- Персональные данные: 152-ФЗ — согласие, политика, локализация БД, срок хранения событий, удаление по запросу.

### 11.4 Безопасность

- Access 15 мин + refresh 30 дней с ротацией и отзывом; никаких токенов в URL.
- Проверки владения на каждом объекте (IDOR-тесты обязательны).
- 2FA для артистов с промо-бюджетом и для всех админов.
- Rate limit: загрузка, регистрация, ответы викторины, события.
- Антифрод: аномальные сессии, одинаковые `ip_hash`, нереалистичная скорость скипов → события не учитываются в скоринге и биллинге.
- Публичный контур: CSP, HSTS, Referrer-Policy, лимиты тела, `X-Request-Id` во всех ответах.

## 12. Монетизация

### 12.1 Промо артистов (основной доход на старте)

- Артист создаёт кампанию: трек, бюджет, период, гео/жанр-таргетинг, ставка.
- Промо-трек попадает в **выделенный слот** волны, а не подмешивается в органику незаметно.
- Ограничения: ≤ 1 промо на 10 треков, ≤ 2 от одного артиста в час, пометка «промо» в UI.
- Оплата за дослушивание ≥ 30 с (защита от накрутки), а не за показ.
- Отчёт артисту: показы, дослушивания, скипы, прирост подписчиков, расход.

### 12.2 Реклама в эфире

- Слоты 15–30 с, ≤ 5% времени, не две подряд, не первая в сессии.
- Таргетинг: жанровый профиль, гео, время суток. Без чувствительных категорий.
- Учёт: `played_ratio` (сколько реально прослушано), а не факт выдачи.
- Маркировка: `erid` в аудио-подводке и в карточке, отчёт в ОРД.

### 12.3 Лейбл

- **A&R-скоринг:** `0.35·retention + 0.25·growth_7d + 0.20·saves_rate + 0.10·follow_conversion + 0.10·catalog_depth`.
- Порог входа в воронку: ≥ 1000 дослушиваний за 30 дней и retention > 55%.
- Договор: шаблон от LEGAL, ставка роялти, срок, территория, права.
- Роялти-учёт: `royalty_ledger` по периодам, прозрачная выгрузка для артиста.
- Дистрибуция: выгрузка релизов на внешние площадки — отдельный проект после Ф4.

### 12.4 Подписка (опция, после Ф4)

Без рекламы, HQ-звук, ранний доступ к релизам, расширенная статистика для артиста. Включать только если радио доказало удержание; считать каннибализацию рекламного дохода.

### 12.5 Модель для проверки (порядок цифр, не прогноз)

Допущения: 20 ч эфира на слушателя/мес · 3 рекламных слота/час · fill 60% · 1% артистов на лейбле × 3 000 ₽/мес.

| MAU | Доля артистов | Конверсия в промо | Чек | CPM | Промо | Реклама | Лейбл | Итого/мес |
|---|---|---|---|---|---|---|---|---|
| 50 000 | 2% | 15% | 1 500 ₽ | 120 ₽ | 225 000 ₽ | 216 000 ₽ | 30 000 ₽ | **471 000 ₽** |
| 200 000 | 2% | 15% | 1 500 ₽ | 120 ₽ | 900 000 ₽ | 864 000 ₽ | 120 000 ₽ | **1 884 000 ₽** |

Пересчитать после первых реальных данных беты. Себестоимость часа эфира (TTS + трафик + хранение) вычесть отдельно — см. §13.3.

## 13. Аналитика и метрики

### 13.1 Схема события

| Расфокус на 5 платформ | Высокая | Высокое | ADR-0016, заморозка, 80% ресурсов в web+API+эфир | PO |
| Накрутки промо и прослушиваний | Средняя | Высокое | Оплата за дослушивание, антифрод событий, ручная проверка выбросов | SEC / DATA |
| Миграция SQLite→Postgres с потерей данных | Низкая | Критическое | Двойная запись, сверка counts/sha256, откат, бэкап перед стартом | BE / OPS |
| Один человек = узкое место | Высокая | Высокое | Роли-агенты + жёсткие гейты, документация как контракт | PO / TL |

## 16. Non-goals

Что **не делаем** в горизонте этого плана (пересмотр — только через ADR):

- Соцсеть с лентой, репостами и бесконечным скроллом.
- Видеоконтент, клипы, стримы артистов.
- DAW, редактор аудио, мастеринг как услуга.
- NFT, токены, криптоплатежи.
- Собственный каталог мейджор-лейблов и переговоры с ними.
- Развитие desktop и console (заморожены).
- Серверный live-mix до Ф5.
- Автоматическая дистрибуция на внешние площадки до отдельного проекта после Ф4.
- Полная автоматизация модерации без человека.

- [ ] Нет дефектов S1/S2; известные ограничения записаны.

### 17.2 Специфичные гейты

| Контур | Дополнительное условие |
|---|---|
| Загрузка | Файл 0 байт, 500 МБ, не-аудио с `.mp3`, юникод и `../` в имени — обработаны |
| Модерация | Трек не публичен до решения; takedown скрывает контент во всех клиентах |
| Волна | Час эфира без ручного вмешательства; правило 90 с проверено автотестом |
| Речь | Ни одна реплика не уходит в эфир без шаблона и кэш-ключа |
| Реклама | Кампания без `erid` не активируется; две подряд невозможны |
| Деньги | Идемпотентность платежей, двойное списание невозможно, возврат проходит |
| Миграция | Сверка количества и sha256 до/после, откат проверен на копии |

### 17.3 Тестовая пирамида

- **Контрактные тесты API** — каждый эндпоинт v2, включая ошибки и права.
- **Юнит** — планировщик эфира (правила 1–12), ранжирование, антифрод, биллинг.
- **E2E (Playwright)** — регистрация → загрузка → модерация → публикация → волна → скип → викторина → промо.
- **Нагрузочные** — 1000 одновременных сессий волны, p95 старта < 1.5 с.
- **Ручные** — прослушивание часа эфира на предмет склеек, громкости, раздражающих вставок (обязательно перед релизом Ф3).

### 17.4 Stack Ready gate до приложений (ADR-0021)

Клиентские продуктовые фичи не начинаются, пока владелец не примет backend-гейт: API F1–F3 с контрактными/permission tests; Postgres migration/rollback/restore; storage URL+takedown; queue idempotency/retry/DLQ; закрытый ingest→moderation pipeline; events/recsys offline metrics; radio/voice integration tests; CI smoke и проверенные staging/runbooks/observability. Полный список критериев и внешних блокеров — `docs/adr/0021-backend-first-before-apps.md`. Технический gate сам по себе не является юридическим разрешением на публичный UGC или запуск.

## 19. Приложения

### 19.1 Системные промпты новых ролей

Копировать в начало задачи соответствующему агенту. Общие правила для всех: отвечать на русском, структурированно; не менять контракт API без правки этого документа; спорное решение оформлять ADR; каждое предложение — с измеримым критерием.

**LEGAL**

> Ты юрист музыкальной платформы Vision. Контур: права на UGC (оферта, подтверждение прав, notice-and-takedown, repeat-infringer), публичное исполнение и договоры с правообладателями, маркировка рекламы (ОРД/erid/ЕРИР), договоры лейбла и роялти, персональные данные. Каждый риск оформляй: severity + конкретный документ или шаблон + шаг внедрения. Не блокируй продукт — предлагай безопасную конструкцию. Явно помечай, где нужна очная консультация профильного юриста, а где достаточно шаблона.

**GROWTH**

> Ты Growth/A&R-менеджер Vision. Воронка: артисты → активные слушатели → лейбл. Организуй закрытую бету (10 артистов + 50 слушателей), веди канал обратной связи, строй скоринг артистов по удержанию, skip-rate и росту лайков. Программа лейбла: условия, роялти, релизный цикл. Метрики: WAU/MAU, D7/D30, число артистов с 1000+ дослушиваний. Каждое предложение — с гипотезой, метрикой и стоимостью проверки.

**TRUST**

> Ты Trust & Safety-лид Vision. Модерация загрузок: автоматическая проверка прав (audio fingerprint), очередь ручной модерации, жалобы, блокировки, апелляции. Политика контента: запрещённые категории, спам, накрутки. SLA реакции на takedown ≤ 24 часа. Артефакты: политика, инструкции модераторов, метрики (время реакции, доля ложных срабатываний, доля оспоренных решений). Балансируй скорость и справедливость: ошибочная блокировка своего трека — тоже инцидент.

**RECSYS**

> Ты ML/RecSys-инженер Vision. Строй ядро «Моей волны»: событийный лог, аудио-эмбеддинги (ONNX), профиль вкуса, кандидаты через ANN и ранжирование (свежесть, разнообразие, знакомое/новое). Промо не подмешивай в score — оно занимает отдельный слот с капом. Метрики: skip-rate < 25%, покрытие каталога > 80%, подборка < 300 мс p95. Cold start — онбординг-выбор. Приватность: обезличенные события, хеши вместо PII. Каждое решение — ADR + офлайн-оценка перед A/B.

**DATA**

> Ты Data-инженер Vision. Событийная шина прослушиваний и эфира, витрины для рекомендаций и A&R-скоринга, дашборды продукта (D1/D7/D30, skip-rate по типам сегментов, время до первого звука), A/B-платформа. Следи за качеством данных: дедупликация, антифрод, единые словари. Приватность: хеши IP, никакой PII в аналитике. Каждый дашборд отвечает на конкретное продуктовое решение, а не «показывает цифры».

**RADIO**

> Ты продюсер живого радио Vision «Моя волна». Проектируй сетку эфира: музыкальные блоки, ведущие, викторины, лайфхаки, погода, брейкньюз, реклама. Пиши сценарные шаблоны и правила частоты, tone of voice — живой, тёплый, без канцелярита, одна мысль на реплику. Главное правило: вставки не разрушают поток, ≤ 90 секунд подряд без музыки. Артефакты: сетка, сценарии, контент-политика, метрики удержания на каждом типе вставки.

**VOICE**

> Ты Voice/AI-инженер Vision. Отвечаешь за TTS-ведущих: выбор движка, тембры, эмоция, произношение имён артистов, кэш синтезированных реплик, микс с музыкой (ducking −6 dB, единая лаудность −14 LUFS). Следи за стоимостью секунды синтеза и задержкой генерации, целевой cache hit-rate > 60%. Новости не синтезируй без редакторской проверки фактов. Не имитируй реальных людей.

**ADTECH**

> Ты AdTech/монетизация-инженер Vision. Строй ad-server «Моей волны»: слоты, таргетинг по вкусу и гео, frequency cap, аукцион промо-бустов артистов, биллинг с чеками и возвратами, отчётность с erid/ОРД. Антифрод показов и прослушиваний, оплата за дослушивание ≥ 30 с. Метрики: fill rate > 60%, eCPM, доля рекламы ≤ 5% эфира, churn после вставок. Промо не должно ломать доверие слушателя к волне.

### 19.2 Шаблон ADR

Структура документа `docs/adr/NNNN-*.md`:

- **Заголовок:** ADR-NNNN: решение. Дата, статус (proposed / accepted / superseded), владелец (роль).
- **Контекст:** что за проблема, какие ограничения, что уже есть в коде.
- **Варианты:** 1–3 варианта, у каждого плюсы, минусы, стоимость.
- **Решение:** что выбрали и почему.
- **Последствия:** что придётся переписать, какие риски, что откатываемо, что нет.
- **Как проверим:** метрика или тест, подтверждающий, что решение работает.

### 19.3 Шаблон задачи для агента

**Задача Ф3.4 — Сценарный движок подводок.** Роли: RADIO + VOICE. Контекст: §9.2, §10.1.

- **Вход:** `prev_track` (метаданные), `next_track`, время суток, гео, погода, профиль вкуса.
- **Выход:** текст реплики ≤ 180 символов + ключ кэша + mix-метаданные.
- **Критерии приёмки:**
  - Given предыдущий трек известен, When строится подводка, Then в тексте есть его название без искажений.
  - Given имя артиста в словаре произношения, When синтез, Then используется фонетическая подсказка.
  - Given та же пара (текст, голос), When повторный запрос, Then синтеза не происходит (кэш).
  - Given длина > 180 символов, When рендер, Then текст сокращается по правилам, а не обрезается на середине слова.
- **Не делать:** новости без факт-чека, имитацию реальных людей, реплики длиннее 15 секунд.
- **Тесты:** юнит на шаблоны, контракт на `/radio/:session/next`, ручное прослушивание 10 подводок.

## Приложение A. Что можно вырезать без потери ядра

Если ресурс — один человек + агенты, минимальный жизнеспособный маршрут:

**Ф0 (вся)** → **Ф1.1–Ф1.7, Ф1.9, Ф1.10, Ф1.12** → **Ф2.1, Ф2.2, Ф2.4, Ф2.5, Ф2.6, Ф2.8** → **Ф3.1–Ф3.4, Ф3.10, Ф3.12** → **Ф4.1, Ф4.2, Ф4.5, Ф4.6** → **Ф5.1, Ф5.5, Ф5.6**

Это даёт: аккаунты → модерация → вкус → живой эфир с ведущим → промо артистов → рост. Всё остальное — надстройки, которые можно добавить после первых денег и первых удержанных слушателей.

**Что нельзя вырезать ни при каких условиях:** модерация и права (Ф1.5–Ф1.7), правила эфира (Ф3.1), лаудность и склейки (Ф3.10), эфирная аналитика (Ф3.12), антифрод денег (Ф4.6).
