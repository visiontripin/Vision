# Runbook: запуск, деплой, бэкапы

## 1. Локальный запуск

```bash
npm install
npm run build        # web → apps/web/dist
npm start            # API + статика, http://0.0.0.0:4000
```

Проверка: `curl -s localhost:4000/api/health` → `{"ok":true,...}`.

## 2. Docker

```bash
docker build -t vision-audio .
docker run -d --name vision \
  -p 4000:4000 \
  -e VISION_PASSWORD='свой-пароль' \
  -e VISION_SECRET="$(openssl rand -hex 32)" \
  -v /srv/vision-data:/app/data \
  --restart unless-stopped \
  vision-audio
```

Данные (`vision.db`, `media/`, `covers/`) лежат в томе `/app/data` — его и бэкапим.

В образ попадают обе сборки: веб-приложение и панель администрирования (`/admin`).
Если панель нужна на сервере — ничего дополнительно делать не нужно; отдельными
каналами идут APK и установщик Windows (`apps/console`, см. `docs/adr/0009-server-console.md`).

## 3. Reverse proxy (TLS)

Caddy — самый короткий путь:

```
music.example.com {
    encode zstd gzip
    reverse_proxy 127.0.0.1:4000
}
```

Проверить после включения HTTPS: вход, загрузка, seek в треке, обложки.

**Для приватных ссылок прокси обязан пробрасывать Host** (Caddy делает это по умолчанию,
nginx — `proxy_set_header Host $host;`). Иначе `/s/<token>` соберёт относительный `og:url`
и карточка в мессенджере развернётся с чужим адресом. Если сервис стоит за прокси с
нестандартным доменом, проще задать `PUBLIC_URL=https://music.example.com` — он
приоритетнее заголовков запроса.

## 4. Бэкап и проверка восстановления (v0.24.0, D5)

Три способа делают **одну и ту же** резервную копию: снимок базы через
`VACUUM INTO` (консистентный на живой базе), медиа и обложки, `manifest.json`,
затем проверка. Отличаются только тем, кто их запускает.

| Способ | Когда | Команда |
|---|---|---|
| Приложение/панель | «сделать копию сейчас» | `POST /api/backups` (или вкладка «Копии» в панели) |
| Скрипт | по cron, сервер не нужен | `./scripts/backup.sh /srv/backups` |
| Сервер сам | расписание, `BACKUP_EVERY_HOURS` | `BACKUP_EVERY_HOURS=24 npm start` |

```bash
# бэкап без остановки сервиса (проверка встроена: при провале код выхода 2)
./scripts/backup.sh /srv/backups

# что было проверено — видно в манифесте
tar -xzOf /srv/backups/vision-2026-11-11_1200.tar.gz ./manifest.json

# проверить архив ещё раз, в любой момент и на другой машине
node scripts/verify-backup.mjs /srv/backups/vision-2026-11-11_1200.tar.gz
```

**Восстановление**

```bash
systemctl stop vision                     # база должна быть закрыта
mv data data.broken-$(date +%F)           # не затираем то, что есть
mkdir -p data
tar -xzf /srv/backups/vision-2026-11-11_1200.tar.gz -C data   # vision.db, media/, covers/
systemctl start vision
curl -s localhost:4000/api/health | grep '"ok":true'
```

Проверка после восстановления — не «открылась ли страница», а три вещи:

1. `curl -s -X POST localhost:4000/api/backups/verify` с токеном владельца → `ok: true`;
2. открыть 2–3 трека (файл на месте → играет);
3. отозванная до бэкапа ссылка остаётся отозванной, действующая — открывается
   (`curl -sI localhost:4000/s/<token>` → `200`).

**Что проверяет проверка:** `PRAGMA integrity_check` = `ok`; число треков в архиве
совпадает с живой библиотекой; для каждого трека есть файл в `media/` (по имени
`<id>.<ext>` из загрузки или `<checksum>.<ext>` из реплики). Красная проверка не
удаляет архив: разбираться нужен сам файл.

**Ротация:** хранится 14 последних копий (`KEEP_ARCHIVES`, `BACKUP_KEEP` для скрипта).
Копия на том же диске — это не бэкап: `BACKUP_DIR` и каталог для cron должны быть на
другом носителе или синхронизироваться наружу.

`scripts/backup.sh` копирует базу целиком, поэтому `shares` и `share_hits` попадают в
архив вместе с треками. Если `VISION_SECRET` сменился, старые ссылки не пострадают (они
не HMAC, а случайный токен), но подписи медиа внутри гостевой страницы выпускаются
заново — это норма.

**Алерт «бэкапы перестали делаться»:** `GET /api/backups` → `level: "warn"` и `hint`,
если копий нет вовсе или последняя старше 7 дней. На расписание не полагайтесь молча:
`BACKUP_EVERY_HOURS=0` его выключает (так делают на машине, где бэкап снимает cron).

## 5. Мониторинг

- `GET /api/health` → `ok`, число треков, свободное место, версия и статус миграций
  (`migrations.pending` должен быть `0`).
- `GET /metrics` — Prometheus-формат. Пример scrape-конфига:

```yaml
scrape_configs:
  - job_name: vision
    static_configs:
      - targets: ['music.example.com']
    metrics_path: /metrics
    authorization:
      credentials: '<METRICS_TOKEN>'
```

Что смотреть в первую очередь:

| Метрика | Смысл | Повод реагировать |
| --- | --- | --- |
| `vision_http_request_duration_seconds` | p95 по маршрутам | > 0.5 s на `/api/tracks` |
| `vision_http_requests_total{status=~"5.."}` | ошибки | любой устойчивый рост |
| `vision_upload_duplicates_total` | дедуп сработал | норм, если растёт вместе с загрузками |
| `vision_stream_partial_total` / `_full_total` | seek vs целые файлы | рост `_full` — клиент ломает Range |
| `vision_disk_free_bytes` | место | < 15 % диска |
| `vision_auth_failures_total` | подбор пароля | > 5 за 5 минут (дальше включается rate limit) |

- Логи — stdout (JSON при `NODE_ENV=production`), каждый запрос содержит `id`
  (он же `X-Request-Id` в ответе), `method`, `path`, `status`, `ms`.
- Алерты: диск < 15 %, `/api/health` недоступен 2 минуты, рост 5xx,
  `migrations.pending > 0` после обновления.

## 5.1 Подписанные медиа-ссылки

`<audio>`/`<img>` не шлют `Authorization`, поэтому сервер выдаёт HMAC-ссылки
с TTL (`MEDIA_URL_TTL_MS`, по умолчанию 30 минут) через `GET /api/media?ids=`.

- Если после сна ноутбука трек «отвалился» с 401 — это ожидаемо, клиент
  перезапрашивает ссылку (в веб-клиенте есть автоповтор).
- Держите `MEDIA_URL_TTL_MS` коротким (10–60 минут): ссылка попадает в логи
  прокси и историю браузера.
- `VISION_SECRET` должен быть стабильным: при его смене все выданные ссылки и
  токены входа становятся недействительными (это ещё и способ «разлогинить всё»).

## 5.2 Транскодинг opus/aac/HLS (v0.6.0)

Сервер сам перекодирует загруженные треки в фоне: opus 96 kbps (`.ogg`), aac 128 kbps
(`.mp4`) и HLS-нарезку по 6 с, с нормализацией `loudnorm=I=-14:TP=-1.5:LRA=11`.
Результат — в `$DATA_DIR/media/variants` и `$DATA_DIR/media/hls/<trackId>/`.

**Без ffmpeg всё работает как раньше**: `/api/media` отдаёт только `original`,
`/api/health` показывает `ffmpeg.available: false`. Ничего не падает и не ретраится.

Откуда берётся бинарник (по порядку):

1. `FFMPEG_PATH` — явный путь;
2. пакет `ffmpeg-static` (зависимость в `optionalDependencies`; на musl/Alpine и без
   доступа к GitHub при `npm install` он просто не скачивается — это не ошибка);
3. системный `ffmpeg` из `PATH`.

Установка на сервере:

```bash
# Debian/Ubuntu
sudo apt-get install -y ffmpeg        # нужен libopus, aac, loudnorm
# Alpine (база Docker-образа)
apk add --no-cache ffmpeg
# macOS
brew install ffmpeg
```

Проверка после рестарта: `curl -s localhost:4000/api/health | jq .ffmpeg` →
`{ "available": true, "version": "ffmpeg version …" }`.

Переменные:

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `FFMPEG_PATH` | — | путь к бинарнику, приоритетнее остальных |
| `TRANSCODE` | `1` | `0` — выключить очередь целиком |
| `TRANSCODE_CODECS` | `opus,aac` | какие варианты делать |
| `TRANSCODE_NORMALIZE` | `1` | `0` — без `loudnorm` (быстрее, громче/тише) |
| `HLS_ENABLED` | `1` | `0` — не нарезать HLS |
| `HLS_SEGMENT_SECONDS` | `6` | длина сегмента |
| `TRANSCODE_BACKFILL` | `0` | `1` — при старте догнать треки, загруженные до ffmpeg |
| `FFMPEG_TIMEOUT_MS` | `600000` | таймаут одной задачи |

Задачи выполняются по одной в процессе API (транскодинг не блокирует цикл: это
дочерний процесс). После загрузки ответ клиенту не ждёт ffmpeg — трек сразу играет
оригиналом, варианты подхватываются на следующем обновлении ссылок (`/api/media`).
Метрики: `vision_transcode_total{result="opus|aac|hls|error"}`,
`vision_transcode_seconds_total{kind}`.

Место на диске: `media/variants/` (opus ~1/10 и aac ~1/3 веса wav) и `media/hls/`
(примерно вес mp3). Это осознанный обмен: трафик при прослушивании падает в 3–10 раз.
Если диск тесный — `HLS_ENABLED=0` (HLS самая тяжёлая часть), затем `TRANSCODE_CODECS=opus`.
`vision_storage_bytes` считает только оригиналы, варианты в метрику не входят.

## 5.3 PWA и офлайн-копии

`apps/web/public/sw.js` кэширует оболочку и список треков; офлайн-копии аудио
хранит само приложение в Cache Storage (`vision-media-v1`, лимит 512 МБ,
вытеснение по LRU). Ключ копии — `sha256` содержимого (`/__vision-offline/<hash>`,
у старых треков без `checksum` — `/__vision-offline/<id>`): тот же файл под другим
`id` не качается второй раз, а удаление находит копию по любому из двух ключей.
Индекс копий в `localStorage` (`vision.offline.index`) хранит `id`, `hash`, размер
и время — старые записи без `hash` продолжают работать.

Что важно при развёртывании:

- service worker и Cache Storage требуют **secure context**: HTTPS или `localhost`.
  Обратный прокси обязан отдавать TLS — иначе офлайн-функции просто не появятся;
- `/sw.js` и `/manifest.webmanifest` должны отдаваться с правильными типами
  (`text/javascript`, `application/manifest+json`) — сервер это уже делает;
- обновление версии: новый `sw.js` подхватывается при следующем визите, старые
  кэши `vision-shell-*`/`vision-api-*` удаляются в `activate`; `vision-media-*`
  не трогаются никогда (это данные пользователя);
- после смены `VISION_SECRET` подписанные URL меняются, но офлайн-копии играют
  по синтетическому ключу — перекачивать их не нужно.

Проверка руками: DevTools → Application → Service Workers (статус `activated`),
Application → Cache Storage (`vision-shell-v1`, `vision-api-v1`, `vision-media-v1`),
Network → Offline → перезагрузить страницу (должна открыться библиотека).

## 5.4 Панель Vision Server (v0.15.0)

Эксплуатация без curl: приложение для Windows и Android (`apps/console`) или та же
страница на самом сервере — `http://<сервер>:4000/admin`.

- **Подключение**: адрес вида `host:4000` (или `https://…`), пароль владельца.
  На Android сервер обычно в Termux — вводите адрес телефона в Wi-Fi.
- **Диагностика** переводит `/api/health` в три цвета: «готов к работе» / «есть замечания».
  Красное — сервер не отвечает или диск почти кончился; жёлтое — не применены миграции,
  нет ffmpeg, есть файлы без источника, не задан `PUBLIC_URL`.
- **Ссылки**: открытия, срок, комментарии, перевыпуск (новая ссылка копируется в буфер)
  и отзыв. Это не замена `docs/API.md` — только кнопки над теми же вызовами.
- Если `/admin` отвечает 503 «панель не собрана» — выполните `npm run build:console`
  и перезапустите сервер; API и библиотека при этом работают.

## 5.5 Приватные ссылки (v0.12.0)

### Комментарии к секундам (v0.14.0)
- Лента хранится в `share_comments` и привязана к паре «ссылка + трек».
- Удалить спам: `DELETE /api/shares/<id>/comments?commentId=<id>` с токеном владельца,
  либо отозвать ссылку целиком — тогда лента перестаёт отдаваться (`410`).
- Полная очистка: `DELETE /api/shares/<id>?purge=1` уносит комментарии вместе с журналом.
- Троттлинг (8 комментариев в минуту на адрес) считается в памяти процесса: рестарт
  его сбрасывает. Если ссылка утекла в публичный чат и ленту заливают — отзовите ссылку,
  это радикальнее и надёжнее любых лимитов.
- Адреса гостей не видны: в БД только `sha256(secret + ip)`, в логах — `share`/`track`.

Ссылка на трек/плейлист — случайный токен в пути (`/s/<token>`); в БД лежит только
`sha256(token)`, поэтому восстановить адрес нельзя, только перевыпустить. Гость не
получает сессию: он видит страницу, поток (`Range`) и скачивание одной цели.

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `SHARE_DEFAULT_TTL_MS` | `604800000` (7 дней) | срок жизни, если `ttl` не задан |
| `PUBLIC_URL` | из заголовков запроса | публичный адрес для `og:url`/`og:image` и ссылок сидов |

Что стоит знать эксплуатации:

- **Ссылки отзываются данными, а не кодом**: `DELETE /api/shares/:id` ставит
  `revoked_at`; удаление трека/плейлиста отзывает все его ссылки автоматически.
  Полная очистка — `DELETE /api/shares/:id?purge=1` (журнал открытий уходит вместе с ней).
- **Лимит открытий** считает показы страницы. `stream`/`download` пишутся только в
  `share_hits`, поэтому один браузер с десятком Range-запросов не съедает лимит.
  Если гость «потерял» ссылку после обновления страницы — смотрите `plays` и `maxPlays`
  в `GET /api/shares`.
- **Приватность**: `share_hits.ip_hash = sha256(VISION_SECRET + ip)`. Смена
  `VISION_SECRET` обнуляет узнаваемость старых IP (новые хеши не совпадут) — это
  ожидаемо; сырых адресов в БД и логах нет.
- **Ссылка не работает, когда файла нет ни у кого**: страница открывается (`200`), но
  поток отвечает `409 no_source`, пока не появится живой сид (см. `docs/DISTRIBUTED.md`).
- **OG-превью не обновляется** в Telegram/WhatsApp: мессенджеры кэшируют карточку.
  После смены обложки отправьте ссылку с новым токеном (перевыпуск).
- Проверка одной командой: `curl -sI "localhost:4000/s/<token>" | head -1` → `200`
  (или `410` для отозванной).

### Встраивание в блог и oEmbed (v0.16.0)

- **Код берётся из приложения**: «Поделиться ссылкой» → «Встроить». Токен показывается
  один раз, поэтому код собирается из уже выданной ссылки; после перевыпуска старый
  `<iframe>` начнёт отдавать `410` — это ожидаемо, вставьте новый код.
- **Вручную**: замените `/s/<token>` на `/embed/<token>` в адресе. Для светлого фона
  добавьте `?theme=light`. Размеры по умолчанию — 480×180 (трек) и 480×320 (плейлист).
- **oEmbed для CMS/Notion**: `GET /api/oembed?url=<ссылка>` — можно указать как
  `oembed`-провайдера, а страница сама объявляет `<link rel="alternate" type="application/json+oembed">`,
  так что автообнаружение работает без настройки. Принимаются только свои ссылки;
  чужой адрес → `400 invalid_url`. Поставьте `PUBLIC_URL`, иначе в ответе будет адрес,
  собранный из заголовков запроса (за прокси — тот, что пришёл).
- **Лимит открытий виджета не касается**: вставка в чужой блог не увеличивает `plays`
  (иначе одна публикация закрыла бы ссылку), но прослушивания в виджете видны в
  `stats.hits.stream`. Если нужно прекратить и прослушивания — отзовите ссылку.
- **Виджет не грузится в чужой странице**: проверьте, что её заголовки не запрещают
  вложенные фреймы (наш ответ `frame-ancestors *` это разрешает; `X-Frame-Options: DENY`
  на стороне блога или CSP родителя может запрещать — это ограничение их сайта).
- **Проверка одной командой**: `curl -s "localhost:4000/api/oembed?url=$(python3 -c
  "import urllib.parse;print(urllib.parse.quote('http://localhost:4000/s/<token>'))")"`.
- Просмотр виджета без вставки: откройте `/embed/<token>` прямо в браузере.

## 5.6 Журнал действий (v0.17.0, G10)

Ответ на «кто это сделал» — без ssh и grep по логам: журнал лежит в БД (`audit_log`)
и читается владельцем лентой.

- **Что видно**: вход и неудачные попытки входа, загрузка/правка/удаление треков,
  плейлисты, выпуск/отзыв/перевыпуск ссылок, комментарии, открытия ссылок,
  прослушивания и скачивания гостями, старт сервера и применённые миграции.
- **Где смотреть**: панель Vision Server → вкладка «Журнал» (фильтры «Треки / Ссылки /
  Комментарии / Входы»), либо `GET /api/audit?action=track&limit=50` с токеном владельца.
  У каждой записи есть `requestId` — он же в заголовке `X-Request-Id` ответа и в строке
  лога, поэтому «странный ответ» и «строка журнала» сопоставляются однозначно.
- **Приватность**: адрес гостя хранится как `sha256(VISION_SECRET + ip)` (тот же хеш, что
  в `share_hits`), токен ссылки не пишется никогда — только `share_id`. Меняете
  `VISION_SECRET` — старые хеши перестают быть сопоставимыми с новыми, это ожидаемо.

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `AUDIT_ENABLED` | `1` | `0` — не писать новые записи (чтение и чистка работают) |
| `AUDIT_RETENTION_DAYS` | `180` | срок хранения; чистка на старте и при `DELETE /api/audit` |

- **Гостевые визиты схлопываются**: повторное открытие той же ссылки с того же адреса
  в течение 10 минут не создаёт новую строку, а увеличивает `details.repeat`. Поэтому
  «одно открытие, repeat: 7» — это один человек, обновивший страницу семь раз.
- **Журнал не растёт бесконечно**: при старте и по `DELETE /api/audit?keepDays=N`
  записи старше срока удаляются. Если журнал нужен дольше — выгружайте его в бэкап
  (`docs/RUNBOOK.md` §4) до чистки.
- **Ошибка записи не ломает действие**: если БД занята, в лог уходит `audit write failed`,
  а удаление трека всё равно выполняется. Аудит вторичен по отношению к действию.
- Проверка одной командой: `curl -s -H "Authorization: Bearer $TOKEN" "localhost:4000/api/audit?limit=5"`.

## 5.7 Вход по ссылке и «Поделиться» (v0.18.0, F1/F5)

- **Ссылки, которые открывают трек**: `visionaudio://track/<id>?t=90`,
  `visionaudio://play/<id>`, `visionaudio://playlist/<id>?play=1`, а в браузере —
  `https://<сервер>/#/track/<id>/90`. Всё, что не распознано, открывает библиотеку:
  пустого экрана не бывает.
- **«Отправить в…»** в меню трека: на телефоне и в установленной PWA открывается
  системный диалог, на десктопном браузере — копирование текста со ссылкой.
- **Share target**: установленная PWA появляется в системном меню «Поделиться».
  Приходит ссылка или маленький файл → открывается `/share`, где нужно нажать
  «Добавить в библиотеку». Ничего не загружается само.
  Ограничение: Android не передаёт через GET большие файлы; для них — выбор файла
  на странице `/share` или обычная загрузка в библиотеке.
- **Проверка на сервере одной командой**:
  `curl -sI "localhost:4000/share?url=https://x.com/a.mp3" | head -1` → `200`
  и `curl -s localhost:4000/manifest.webmanifest | grep -o '"share_target"'`.
- **Если ссылка из чата не открывает трек**: проверьте, что она указывает на этот
  сервер (`/#/track/…`), а не на старую копию; и что трек ещё в библиотеке —
  удалённый трек ссылка не воскрешает.

## 6. Типовые проблемы

| Симптом | Причина | Решение |
|---------|---------|---------|
| Трек не играет, в Network 401 на `/stream?exp=…&sig=…` | истекла подпись или сменился `VISION_SECRET` | обновите страницу; в API ссылки перезапрашиваются автоматически |
| 409 при загрузке `duplicate` | этот файл уже в библиотеке (SHA-256) | откройте существующий трек из ответа |
| Поиск ничего не находит | FTS-индекс рассинхронизирован (ручные правки БД) | `npm run start` применяет миграции; пересборка индекса — удалить `tracks_fts` и запустить сервис |
| 415 при загрузке | файл не аудио или битые magic bytes | проверьте файл, конвертируйте в mp3/wav |
| 413 | файл > 500 МБ | поднимите `MAX_UPLOAD` в `services/api/src/server.js` |
| Пустая волна | браузер не смог декодировать (flac в Safari) | peaks = null, рисуется псевдо-волна; конвертируйте в mp3 |
| Seek возвращает 200, а не 206 | reverse proxy буферизует ответ | отключите буферизацию для `/api/tracks/*/stream` |
| `SQLite is experimental` в логах | предупреждение Node 22 | безвредно; можно скрыть `--no-warnings` |
| `/api/health` → `ffmpeg.available: false` | бинарника нет в `PATH`, `ffmpeg-static` не скачался | поставьте ffmpeg (см. 5.2) и перезапустите; треки догонятся при `TRANSCODE_BACKFILL=1` |
| `X-Variant-Fallback` в ответе `/stream` | клиент попросил opus/aac, которого ещё нет | норма во время транскодинга или без ffmpeg |
| `404 no_hls` | HLS выключен (`HLS_ENABLED=0`), ffmpeg нет или трек в очереди | проверьте `/api/health`, повторите позже |
| `vision_transcode_total{result="error"}` растёт | ffmpeg падает на конкретном файле | смотрите `lastError` в `/api/health`, лог `transcode`; файл скорее всего битый |
| `ffmpeg.available: true`, но `path` указывает на `ffmpeg-static` | бинарник запускается, значит платформа совпала | норма; на Android такого быть не должно — там glibc-сборка не запускается и резолв уходит в `PATH` |
| `node:sqlite` не найден | Node < 22.5 или нестандартная сборка | обновите Node; на Termux — `pkg upgrade nodejs` |
| Нет кнопки «Скачать офлайн» | страница открыта по http:// (не secure context) | откройте через HTTPS/Tailscale или localhost |
| Service worker в статусе `redundant`/не регистрируется | CSP или MIME для `/sw.js` | проверьте `Content-Type: text/javascript` и `worker-src 'self'` |
| Офлайн-копия есть, но трек не играет офлайн | браузер почистил Storage | перекачайте копию; проверить `navigator.storage.estimate()` |
| Ссылка `/s/<token>` отдаёт `410 отозвана/истекла` | владелец отозвал, сработал TTL или лимит открытий | создайте новую ссылку или перевыпустите (`POST /api/shares/:id/rotate`) |
| Ссылка отдаёт `404` | токен искажён при копировании или ссылка удалена с `purge=1` | выпустите новую; старые токены не восстанавливаются |
| Гость видит страницу, но трек не играет (`409 no_source`) | файл не раздаёт ни один сид | поднимите узел с файлом (`/seed`), проверьте `/api/seeds` |
| В мессенджере нет карточки с обложкой | у трека нет обложки или прокси не пробрасывает Host | загрузите обложку (`PUT /cover`) / задайте `PUBLIC_URL` |
| `og:image` ведёт на внутренний адрес | сервис за прокси без `X-Forwarded-*`/`Host` | задайте `PUBLIC_URL` |

## 7. Обновление версии

```bash
git pull
npm ci
npm run build
npm test
docker build -t vision-audio . && docker rm -f vision && docker run ...   # или systemctl restart vision
curl -s localhost:4000/api/health
```

Миграции БД идемпотентны (`CREATE TABLE IF NOT EXISTS`) и применяются при старте
по порядку номеров; учтённые версии лежат в таблице `schema_version`, статус виден
в `/api/health`. Откат — только восстановлением бэкапа (миграции не «откатываются»).

Перед обновлением всегда:

```bash
./scripts/backup.sh /srv/backups      # база (WAL-safe) + media/ + covers/
npm ci && npm run build && npm test   # 14 контрактных тестов API + 3 теста local-режима
```
