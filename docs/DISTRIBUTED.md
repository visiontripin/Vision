# Распределённое хранение: трекер + сиды (план следующей итерации)

Исходная задача: **серверного хранилища нет**. Файлы должны жить на устройствах —
у того, кто их загрузил, и у тех, кто их слушает. Ответ на вопрос «сделать как в
торрент-трекерах» — «да, но с поправкой на браузер и телефон», ниже почему.

## Что уже есть (фундамент)

| Кусок | Где | Зачем в этой схеме |
| --- | --- | --- |
| SHA-256 каждого файла | `tracks.checksum`, `findByChecksum` | адресация контента: один и тот же файл = один блоб |
| Офлайн-копии в браузере | `apps/web/src/offline.ts` | у слушателя уже есть локальная копия, готовая к раздаче |
| Офлайн-файлы в приложении | `apps/mobile/src/downloads.tsx` | то же на телефоне, с путём в приватном каталоге |
| Подписанные URL + Range | `/api/media`, `/api/tracks/:id/stream` | раздача файла с любого устройства не требует новых протоколов |
| Транскодинг opus/aac | `services/api/src/transcode.js` | лёгкие копии можно раздавать вместо оригиналов |

## Почему не WebRTC/WebTorrent «прямо сейчас»

1. Браузер **не может отдавать файл по HTTP** — у вкладки нет входящего сокета.
   Отдача из браузера возможна только через WebRTC data channels.
2. WebRTC требует signalling (это ок, сервер есть), STUN и — при CGNAT/симметричном
   NAT — **TURN-релей**. TURN это уже трафик сервера, то есть «без серверного
   хранилища» превращается в «серверный трафик» и ежемесячный счёт.
3. Сидирование из браузера работает, только пока открыта вкладка; на телефоне ОС
   убивает фоновую вкладку/приложение. «Каждый сидирует всегда» на практике не выйдет.
4. Integrity и битфилд придётся писать самим (или тащить WebTorrent ~200–400 КБ и
   его трекер-протокол в личный проект).

**Вывод:** транспорт — обычный HTTPS с подписанными ссылками (уже работает), а
«рой» строится на реестре реплик. WebRTC остаётся опцией на потом, когда будет
понятно, что без него не обойтись.

## Целевая схема (v0.9)

```
                 ┌──────────────────────────────┐
   метаданные →  │  сервер-трекер (SQLite)      │  ← маленький, без аудио
   реплики    →  │  tracks / blob_seeds / auth  │
                 └──────────────┬───────────────┘
                                │  «где лежит блоб X»
        ┌───────────────────────┼───────────────────────┐
        ↓                       ↓                       ↓
  Termux (origинал)      десктоп (Tauri)          телефон (Expo, dev build)
  HTTP + Range           встроенный HTTP-сервер   сид только на переднем плане
        │                       │                       │
        └─────────── клиент качает с первого живого сида ───────────┘
                     проверяет SHA-256, кладёт копию, регистрируется как сид
```

### Модель данных

```sql
-- блоб = содержимое (SHA-256), трек = метаданные, ссылающиеся на блоб
CREATE TABLE blobs (
  hash        TEXT PRIMARY KEY,      -- sha256 файла
  bytes       INTEGER NOT NULL,
  mime        TEXT NOT NULL,
  created_at  TEXT NOT NULL
);

CREATE TABLE blob_seeds (
  hash        TEXT NOT NULL REFERENCES blobs(hash) ON DELETE CASCADE,
  device_id   TEXT NOT NULL,         -- устройство-сид (не пользователь)
  kind        TEXT NOT NULL,         -- origin | desktop | mobile | browser
  base_url    TEXT,                  -- откуда качать (у браузера null)
  online_at   TEXT NOT NULL,         -- heartbeat; старше 2 минут = офлайн
  PRIMARY KEY (hash, device_id)
);
```

### API (добавляется к существующему)

- `POST /api/blobs` — объявить блоб: `{ hash, bytes, mime }` (аудио не передаётся).
- `POST /api/blobs/:hash/seed` — heartbeat устройства-сида (раз в минуту).
- `GET /api/blobs/:hash/seeds` — список живых сидов, отсортированный по близости
  (свой origin первым).
- `GET /api/tracks/:id/download` — 302 на первый живой сид, иначе `409 no_source`.
- `POST /api/tracks` в режиме `STORAGE_MODE=metadata` принимает только метаданные
  (`hash`, `size`, `mime`, `duration`, `peaks`) — файл остаётся у загрузившего.

### Правила

- **Не меньше одного живого сида**, иначе трек помечается `no_source` и в интерфейсе
  показывается серым с подсказкой «нет источника».
- **Проверка целостности** после скачивания: SHA-256 обязан совпасть, иначе копия
  удаляется и сид помечается битым.
- **Репликация по прослушиванию**: скачал — стал сидом (для браузера это офлайн-копия
  в Cache Storage; для приложения — файл).
- **Порядок выбора сида**: origin (Termux) → десктоп → телефон → браузер.
- **Сид на телефоне** — только пока приложение на переднем плане; это честно
  документируется, чтобы не обещать «вечный торрент».

### Этапы

1. **Контент-адресация и реестр** (сервер + миграция `007-blobs`): таблицы, API,
   `STORAGE_MODE`, статус «нет источника» в выдаче треков. Тесты — как у обычных
   маршрутов, без сети.
2. **Раздача с устройств**: Termux и десктоп публикуют `base_url` и heartbeat;
   клиент пробует сидов по очереди, проверяет хеш.
3. **Клиентская часть**: публикация офлайн-копии как реплики (один вызов), показ
   «есть у N устройств», ручное удаление реплики.
4. **Опционально** — WebRTC-сид для браузера (WebTorrent), если окажется, что
   HTTPS-сидов регулярно не хватает.

## Что это меняет для Termux

Сервер остаётся, но перестаёт быть хранилищем: диск нужен только под SQLite и
кэш вариантов. Файлы живут в `~/.vision-seed/` и раздаются тем же HTTP-слоем
(уже умеет Range и подписи), поэтому отдельный протокол не нужен.
