# SoundCloud: реверс-инжиниринг продукта и технологий

**Резюме для команды Vision Audio.** Дата: 09.11.2026.
Метод: анализ публичных источников — инженерный блог SoundCloud (`developers.soundcloud.com/blog`),
доклады KubeCon/QCon, документация и поведение публичного API, наблюдаемое поведение веб-клиента
и плеера, отраслевая пресса. Внутренние сервисы, приватный API и мобильные приложения закрыты —
там, где вывод сделан по косвенным признакам, стоит пометка **[вывод]**.

> Юридическая граница: это продуктовая и архитектурная реконструкция по открытым данным.
> Скрейпинг, обход приватного `api-v2` и реверс клиентских токенов в документе не рассматриваются
> как допустимые практики — только как описание того, как устроена защита сервиса.

## 1. Краткая сводка: что такое SoundCloud как система

| Аспект | Суть |
|--------|------|
| Продукт | UGC-платформа аудио: загрузка своих треков, таймкод-комментарии, репосты, плейлисты, волновой плеер. 85% времени прослушивания — пользовательский контент, а не лицензированный каталог |
| Масштаб каталога | 400+ млн треков, 40+ млн артистов, 193 страны (данные компании, ноябрь 2025) |
| Аудитория | ~76 млн месячных слушателей (оценки отрасли; компания MAU не публикует, встречаются оценки 120–175 млн — разброс большой) |
| Архитектура | Ruby on Rails монолит → микросервисы на Scala + Finagle → Kubernetes; публичный API вынесен в BFF и монолит удалён |
| Данные | MySQL как источник правды, Cassandra для части нагрузки **[вывод]**, memcached, Kafka как шина событий, Elasticsearch для поиска (1 млрд документов) |
| Аудио | Транскодинг при загрузке → HLS-сегменты, кодеки mp3/opus/aac; 128 kbps для free, 256 kbps для Pro/Go+ |
| Волна | Считается один раз на сервере при загрузке → PNG в CDN + JSON-эндпоинт с семплами |
| Фронтенд | SPA с 2012 (Backbone.js, «Next SoundCloud»), постоянный нижний плеер, выделенный api-v2 для клиентов |
| Монетизация | Реклама + подписки слушателя (Go/Go+) + подписки артиста (Artist/Next Pro) + дистрибуция (Repost) + fan-powered royalties |

## 2. Продуктовая карта функций

### 2.1 Контент и библиотека
- **Трек**: файл + название, исполнитель, альбом/жанр, описание, обложка, теги, дата, лицензия, счётчик прослушиваний/скачиваний/лайков/комментариев/репостов.
- **Плейлисты и альбомы**: упорядоченные коллекции, обложка, описание, счётчик прослушиваний; альбом отличается от плейлиста позиционированием у артиста.
- **Приватные треки**: доступ по «секретной» ссылке с токеном в URL — трек не индексируется, но воспроизводится у любого, кто знает ссылку. Дешёвый шаринг без аккаунта.
- **Скачивание**: опция у автора (оригинальный файл, не транскод), скачивание может быть разрешено только для скачавших/подписчиков **[частично подтверждено]**, у платных тарифов — без ограничений.
- **Лимиты загрузки**: тарифные (бесплатный — ограниченное время звучания; Artist — ограничение загрузок в месяц, Next Pro — «безлимит» в рамках fair use). Точные пороги меняются, проверять в Help Center перед копированием.

### 2.2 Социальный слой (главный дифференциатор)
- **Таймкод-комментарии**: комментарий привязан к позиции в треке и рисуется поверх волны; можно отключить у трека, модерировать, отвечать. Превращает пассивное прослушивание в общение вокруг конкретного такта.
- **Лайки и репосты**: репост публикует трек в ленте подписчиков репостнувшего; репост-цепочки — механизм вирусности и одновременно источник спама.
- **Подписки и лента**: активность тех, на кого подписан (треки/репосты/плейлисты).
- **Сообщения и уведомления**: личные сообщения, уведомления о лайках/репостах/комментариях/подписках.
- **Профили**: аватар, баннер, bio, ссылки, статистика, витрина треков и плейлистов.

### 2.3 Плеер и прослушивание
- **Постоянный нижний плеер**: звук не прерывается при переходе между разделами (SPA-«рамка» вокруг контента) — с 2012 года и по сей день.
- **Волна**: интерактивная, клик = seek; на ней же маркеры комментариев; масштабирование под ширину экрана (рисуется на canvas из семплов, а не тянется картинкой в натуральном размере).
- **Очередь и «Next up»**, shuffle, repeat, регулировка громкости, «продолжить слушать», история.
- **Качество**: выбор качества на платных тарифах (Go+ — 256 kbps AAC), на free — 128 kbps MP3.
- **Медиа-интеграции**: Media Session (кнопки на клавиатуре/в ОС), фоновое воспроизведение в мобильных приложениях, офлайн-режим у подписчиков.
- **Embed-виджет**: iframe-плеер для внешних сайтов + oEmbed — основной способ распространения в блогах и медиа.

### 2.4 Обнаружение (discovery)
- **Поиск**: по трекам/людям/плейлистам, поиск по тегам и жанрам, сортировки; релевантность исторически слабое место на каталоге в сотни миллионов записей.
- **Чарты**: топы по жанрам и странам на основе прослушиваний за период.
- **Stations**: «радио» от трека/артиста — бесконечный поток похожего.
- **Рекомендации**: «related tracks», персональные подборки, редакционные подборки.
- **AI-слой**: в 2022 куплена **Musiio** (Сингапур) — модель, которая «слушает» аудио, автоматически тегирует, ищет похожее и помогает строить плейлисты. Куплена именно под discovery и аналитику трендов.
- **Редакция**: медийные форматы (The Upload, премьеры, подборки) — ручное кураторство поверх алгоритмов.

### 2.5 Инструменты автора
- Загрузка (drag&drop, метаданные, обложка, расписание релиза), управление треками, замена файла **[вывод]**.
- Статистика: прослушивания, скачивания, лайки, комментарии, репосты, география слушателей, источники трафика.
- Монетизация: подключение к партнёрской программе, выплаты, **fan-powered royalties** (2021) — доход делится по фактическому прослушиванию конкретного фаната, а не по глобальному пулу.
- **Дистрибуция** (Repost/SoundCloud for Artists): доставка релизов в Spotify, Apple Music и др.; с ноября 2025 компания отказалась от своей доли роялти дистрибуции (артист забирает 100%).
- **Fan Support**: кнопка прямого доната от фанатов, без комиссии платформы (запуск в США).
- **Copyright**: автоматическая проверка загрузок на совпадения с правообладателями, споры и снятия.

### 2.6 Клиенты и платформа
- Web (основной), iOS, Android. Официальных нативных приложений для Windows/Linux/macOS нет — только веб.
- Публичный API + внешние приложения; регистрация новых приложений фактически закрыта с ~2017–2019, а с июля 2021 `client_id` в query заменён на OAuth `client_credentials` — это ответ на массовый абьюз «утекших» client_id из JS-бандла.
- Ограничения: rate limit (429 при агрессивных запросах), отсутствие части полей в публичном API, отдельный внутренний `api-v2` для собственных клиентов.

## 3. Техническая архитектура: как это сделано

### 3.1 Эволюция бэкенда

| Период | Что происходило |
|--------|-----------------|
| 2007–2011 | Единое Ruby on Rails-приложение обслуживает и сайт, и публичный API |
| 2012 | «Next SoundCloud»: сайт становится SPA на Backbone.js, данные — через API; появляется постоянный плеер |
| 2014 | Разъезд по микросервисам. Rails признан плохим клиентом для десятков сервисов, публичный API выделяют в прокси-сервис на Scala/Finagle (Strangler pattern). Scala становится основным языком бэкенда |
| 2015–2019 | Docker + Kubernetes (один из ранних крупных адоптеров), Prometheus (создан в SoundCloud в 2012) как стандарт мониторинга |
| 2020 | Twinagle: собственная реализация протокола Twirp для Finagle + Protobuf вместо JSON на межсервисном уровне. Замер: −40% сетевого трафика |
| 2022 | Переезд публичного API завершён: Rails-код API удалён, остался Scala-BFF |

**Почему Scala + Finagle.** Finagle моделирует сервис как функцию `Req => Future[Rep]`, даёт неблокирующий I/O на Netty, таймауты, ретраи, circuit breaking, клиентский load balancing и service discovery из коробки. Вокруг него — внутренняя библиотека **jvmkit**: обёртки над Finagle HTTP/memcached/MySQL с дефолтами, DNS-SRV service discovery, роутинг, JSON, логирование по стандарту, feature toggles.

**BFF.** Публичный API — не «API монолита», а Back-end-for-Frontend: собирает ответы из десятков сервисов, кэширует, скрывает внутреннюю топологию, обеспечивает консистентность и безопасность. Это тот же паттерн, который нужен любому продукту с несколькими клиентами (web/mobile/desktop).

### 3.2 Данные и поиск

```
Загрузка/изменение → eventfeeder → indexer → MySQL (источник правды)
                                        ↓
                                   Kafka (log-compacted: только последняя версия документа)
                                        ↓
                                    shipper → Elasticsearch (bulk)
```

- **MySQL** — primary store метаданных.
- **Kafka** с log compaction — «журнал состояния»: пересоздание поискового кластера = сброс offset у shipper и replay.
- **Elasticsearch**: 3 независимых кластера с одним и тем же датасетом, по 30 нод (150 GB SSD, 64 GB RAM, 32 ядра) → ~2 ТБ RAM и ~1000 ядер, >1000 поисковых запросов/с в пике. Полный реиндекс ~1 млрд документов — за час.
- **memcached** — кэш горячих объектов (профили, треки, счётчики).
- **Cassandra** — для счётчиков/лент/таймлайн-данных **[вывод по публичным докладам команды]**.

Урок: поиск не «внутри базы», а отдельный конвейер с идемпотентным replay. Это позволяет менять схему индекса без потери данных и без миграций «на живую».

### 3.3 Аудио: загрузка → транскодинг → доставка

1. **Upload** — файл принимается, валидируется, оригинал сохраняется в объектное хранилище (S3-совместимое).
2. **Транскодинг** — из оригинала делаются потоковые варианты: 128 kbps MP3 (free), 256 kbps MP3 (Pro), 256 kbps AAC (Go+). Оригинал остаётся для скачивания, если автор разрешил.
3. **Нарезка в HLS** — трек режется на короткие сегменты + плейлист с URL и таймингами. Основной протокол доставки — HLS; кодеки — mp3, opus, aac.
4. **CDN** — сегменты и волна раздаются с `*.sndcdn.com`, длинный кэш, подпись/токены для приватных треков.
5. **Клиент**:
   - `HTML5Player` — просто отдаёт URL+MIME в `<audio>`;
   - `HLSMSEPlayer` — свой слой поверх Media Source Extensions, который собирает поток из сегментов;
   - «Maestro» — библиотека обходов браузерных багов (разные версии Safari/Chrome ведут себя по-разному);
   - **progressive streaming через `fetch()`** — данные качаются вручную и подаются в MSE; при обрыве байты отбрасываются и запрос повторяется; буфер умеет ждать «целые» единицы аудио, если сегмент пришёл частично.

Почему HLS, а не просто прогрессивный файл: адаптивность (переключение качества на лету), быстрый старт, мелкая гранулярность кэша, лучшее поведение при seek и мобильных обрывах. Цена — сложность пайплайна и необходимость MSE (в Safari — свой HLS-стек).

### 3.4 Волна (waveform)

- При обработке загрузки сервер считает амплитудные пики и **рендерит PNG**, который кладётся в CDN: `https://w1.sndcdn.com/<hash>_m.png`.
- В публичном API трека есть `waveform_url`; если заменить `.png` на `.json` — вернётся `{width, height, samples: [...]}`. Исторически «Next SoundCloud» вытаскивал данные, анализируя пиксели PNG на клиенте, затем это перенесли на бэкенд, а позже добавили JSON.
- Клиент рисует волну на `<canvas>` в нужных размерах из семплов — картинка не мылится при ресайзе.

Урок: волну нужно считать **один раз при загрузке** и хранить как компактный массив. В Vision Audio это делает браузер при загрузке (180 пиков, RMS) — тот же принцип, но без ffmpeg на сервере.

### 3.5 Фронтенд

- 2012: SPA на Backbone.js, CommonJS→AMD-модули, шаблоны прекомпилируются, CSS — зависимость view и подключается при рендере.
- Ключевая UX-идея: **оболочка с плеером живёт вне роутинга**, контент подгружается в неё — отсюда «непрерывный звук» при переходах.
- Сегодняшний веб — эволюция той же модели: клиент ходит в `api-v2`, client_id/токен живёт в бандле, тяжёлые данные (волна, комментарии) подгружаются лениво по мере скролла и раскрытия трека.
- Мобильные приложения — нативные оболочки с фоновым аудио и офлайн-кэшем для подписчиков; конкретный стек публично не документирован.

### 3.6 Инфраструктура и эксплуатация
- AWS, контейнеры, Kubernetes (с 2015), собственный контроллер деплоя и service discovery поверх DNS.
- **Prometheus** родился в SoundCloud (2012) — метрики pull-моделью, затем Grafana.
- Feature toggles — обязательная часть jvmkit: выкатка функциональности без релиза клиента.
- Клиентский load balancing и таймауты/ретраи на уровне Finagle вместо «умного» балансировщика.

### 3.7 Безопасность и антиабьюз
- OAuth `client_credentials` для серверных интеграций вместо `client_id` в query (с 2021).
- Rate limiting на API (429), закрытая регистрация приложений.
- Приватные треки — токен в URL, неугадываемые идентификаторы.
- Copyright-скан загрузок, ручная модерация жалоб.
- Ограничения тарифов как антиабьюз (лимиты загрузки, время звучания).

## 4. Десять решений, которые стоит изучить (и цена каждого)

| # | Решение SoundCloud | Зачем | Цена / риск |
|---|--------------------|-------|-------------|
| 1 | Микросервисы на Scala/Finagle + jvmkit | Независимые деплои, единые таймауты/ретраи/метрики | Высокий порог входа, 200+ сервисов — оверкилл для малого продукта |
| 2 | Публичный API как BFF, а не «дырка в монолит» | Клиенты не знают внутренней топологии | Нужна дисциплина контрактов и версионирования |
| 3 | Kafka как log-compacted журнал документов для поиска | Реиндекс 1 млрд документов за час, без миграций | Эксплуатация Kafka ради одной задачи — избыточно |
| 4 | HLS + собственный MSE-слой | Адаптивность, быстрый старт, устойчивость к обрывам | Нужен транскодер, нарезчик, CDN, обходы браузеров |
| 5 | Прекомпьют волны → PNG/JSON в CDN | Дешёвый рендер, кэш, нет нагрузки на API | Нужно пересчитывать при замене файла |
| 6 | Постоянный нижний плеер вне роутинга | Музыка не прерывается — базовое ожидание пользователя | Усложняет состояние и code-splitting |
| 7 | Таймкод-комментарии | Уникальная вовлечённость вокруг контента | Модерация, спам, нагрузка на чтение |
| 8 | Приватные ссылки с токеном | Шаринг черновиков без аккаунта | Утечка ссылки = утечка аудио |
| 9 | Feature toggles на уровне платформы | Выкатка без релиза, A/B | Дисциплина и «зомби-флаги» |
| 10 | Prometheus/метрики с первого дня | Видно деградацию до жалоб | Нужны SLO и алерты, иначе шум |

## 5. Особенности и «квирки», которые замечает пользователь

**Продуктовые**
1. **128 kbps по умолчанию** и отсутствие нормализации громкости: тихие и громкие треки звучат по-разному, «громкий» мастер выигрывает. Для личного продукта это решаемо ReplayGain-нормализацией.
2. **Волна-картинка**: PNG с CDN + `.json`-трюк с семплами — элегантно, но данные нестандартизированы.
3. **Репост-лента** легко превращается в спам: репост одного и того же трека десятком аккаунтов вытесняет новое.
4. **Приватные треки по ссылке** живут вечно, отзывать доступ неудобно.
5. **Поиск и дедупликация** на каталоге 400 млн записей — слабое место: одинаковые треки, реаплоады, «битые» метаданные.
6. **Мобильный офлайн** только у подписчиков; бесплатный пользователь зависит от сети.
7. **Нет официального десктоп-клиента** для Windows/Linux — только браузер (и сторонние обёртки).
8. **Публичный API почти закрыт** — экосистема сторонних клиентов деградировала; исторически `client_id` «утекали» из веб-бандла и использовались всеми.
9. **Тарифные лимиты** (время звучания, число загрузок в месяц, качество) — главный источник раздражения авторов.
10. **Модерация и copyright** — автоматические снятия и споры; UGC-природа делает это неизбежным.

**Инженерные**
- Плеер и «страница» живут в разных жизненных циклах — состояние трека не сбрасывается при навигации; это надо проектировать сразу.
- HLS ломает простые вещи: `currentTime`, длительность, seek до загрузки манифеста, кэш Range.
- Волна и комментарии — самые «тяжёлые» для рендера части; их грузят лениво.
- Перенос публичного API занял 8 лет: Strangler-паттерн работает, но это марафон, а не спринт.

| Монетизация | реклама, Go/Go+, Artist/Next Pro, дистрибуция, fan-powered royalties | Тарифы и условия меняются, сверять с Help Center |
| Роялти | fan-powered с 2021; с ноября 2025 — 0% комиссии дистрибуции | Пресс-релизы компании |

Вывод для Vision Audio: масштаб SoundCloud — следствие сетевых эффектов и UGC, а не технологий.
Копировать нужно **механику** (непрерывный плеер, волна, таймкод-комментарии, приватные ссылки,
fan-powered логика выплат), а не инфраструктуру под 400 млн треков.

## 7. Что НЕ стоит копировать

1. **Микросервисы на старте.** Для одного пользователя (или тысячи) монолит + SQLite/Postgres быстрее и надёжнее.
2. **Kafka/Elasticsearch «на всякий случай».** FTS5 в SQLite покрывает личную библиотеку до сотен тысяч треков.
3. **HLS сразу.** Прогрессивный Range-стриминг проще и достаточен, пока нет адаптивного битрейта и мобильных сетей с потерями.
4. **Соц-слой по умолчанию.** Репосты/лента/подписки имеют смысл только при аудитории; в личном продукте это мёртвый код.
5. **Закрытый API.** Для своего продукта наоборот: стабильный контракт + токены = возможность писать скрипты и клиентов.
6. **«Умный» балансировщик вместо клиентских таймаутов.** Начните с таймаутов и health-check.
7. **Огромный SPA-бандл с водопадом запросов.** SoundCloud платит за это годами; у нас есть шанс сделать проще.

---

## 8. Переносимые уроки (коротко)

1. Плеер — глобальная оболочка, контент — сменяемая часть.
2. Волна считается один раз и хранится компактно.
3. Приватный доступ — токен в ссылке, отдельно от сессионной авторизации.
4. Медиа-файлы отдаются с поддержкой Range и длинным кэшем; авторизация — короткоживущими подписями, а не «вечным» токеном в query.
5. Поиск — отдельный индекс, а не `LIKE` по основной таблице (как только библиотека > ~5 тыс. треков).
6. Контракт API — версионируемый документ; BFF прячет внутренности.
7. Метрики и health-check с первого дня: Prometheus-модель (pull + `/metrics`) или её упрощённый аналог.
8. Тарифы/лимиты — продуктовый инструмент, но каждая граница раздражает; для личного продукта лимиты не нужны вообще.
